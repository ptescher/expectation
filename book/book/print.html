Expectation

Introduction

Expectation is acceptance testing where the behaviour itself is the source of truth.

You describe a system as expectations: given some state, when something happens, then the system ends up in some state. Every step is written in a shared vocabulary of states and events, so expectations can be compared with each other mechanically, not just run.

Expectation: Turning the dial up starts the kettle
  Given the kettle is off
  When the dial is above 55 %
  Then the kettle is heating

From a suite of expectations, Expectation:

  1. finds conflicts. Two expectations that both apply, and promise incompatible things, are an error. It names the situation where they clash and suggests which one is the exception. You settle it with Overrides:, and overrides must form a DAG.
  2. builds a flow DAG from the starting state. It shows what leads to what, warns about behaviour nothing can reach, and gives every expectation a shortest route from the start.
  3. compiles user stories into acceptance tests. A story only describes the journey. At each step, the expectations it passes through supply the checks. A story that relies on unspecified behaviour, or contradicts an expectation, is rejected before anything runs. Generated tests reach whatever no story does.
  4. runs those tests against your system through a small driver, and takes a screenshot at every step.
  5. writes the documentation: a manual where stories are step-by-step tutorials and features are topic pages, with the test evidence folded away under “How this is tested”, plus a full test report.
.expect files ─language─▶ Suite ─graph─▶ conflicts · override DAG · flow DAG
                            │                         │
                            └────────story────────────┴─▶ plans (acceptance tests)
                                                             │
                                          harness + driver ──┴─▶ report + screenshots ─docs─▶ HTML + Markdown

Writing a suite that also reads as good documentation takes some care: see Feature docs that explain, and its generated feature page.

Why

Most acceptance tests are scripts: do this, check that. Nothing connects one script to the next, so two tests can quietly assume opposite things, and nobody notices which behaviour is never tested at all. Gherkin made scripts readable, but its steps are free text bound to code with regular expressions, so a tool can’t tell what they mean.

Expectation makes the steps mean something. Because every step is a fact about a declared state, or a declared event, the suite is a model of the system. That model can be checked before any test runs. A story doesn’t have to restate every outcome, because the expectations already promise them. And the same model, written in the user’s words, is good enough to publish as the user manual.

What it is not

  • It doesn’t drive your UI for you. You write a driver (usually a dozen closures) that sets states, makes events happen and reads states back. Anything you can control from Rust can be tested: a library, a game loop, a web app through its API or a browser, a device over a serial line. A driver can also be JavaScript or Swift, in the app or in a browser-automation test, talking to the runner over HTTP.
  • It doesn’t model data. States are named values and numbers, not strings or records; Modelling an app with data says how a product full of records is written.
  • It isn’t a property-based tester. Generated tests follow the shortest routes through the flow graph to cover every expectation; they don’t search for counterexamples.

The short version

In a project that already uses Expectation, install it the way the project does (its setup script, or the revision its README or CI pins), so the command, the runner and the client match the suite. Otherwise pin one:

rev=$(git ls-remote https://github.com/ptescher/expectation HEAD | cut -f1)   # no tagged releases yet
cargo install --git https://github.com/ptescher/expectation --rev "$rev" expectation_cli
expectation init expectations               # a starter suite, for a new project
expectation check expectations              # errors exit 1
expectation plan expectations --coverage    # the tests the stories compile to
expectation docs expectations docs          # the manual

A suite is every *.expect file under a directory: a vocabulary of states and events, expectations (given, when, then), and stories that become tutorials and tests. The language is the reference.

Rules that matter

  • Don’t invent behaviour. For a product that exists, inspect it. For a feature that isn’t built yet, the suite is the specification: write what was asked, mark it Status: pending and Approval: proposed, and follow Spec first. Either way, if something is undecided, write Unresolved: <question> in the description (plain text, not a keyword), mark it Approval: proposed, and ask.
  • A driver has one handler per word of the vocabulary: observe and arrange for a state’s subject, on for an event. Getting started without Rust and Drivers show one. A word with no handler makes its tests “not supported yet”; don’t fake one to make a test pass.
  • States are named values or numbers, not strings or records. See Modelling an app with data.
  • Write the explanation and the expectations together, then check, plan, generate and read the pages. See Feature docs that explain.
  • Stories become tutorials, so they teach the feature: a real goal, the path a user would take, how it works and how to read the result. Not a sequence of test steps. See What a story needs.
  • Map the product’s user goals to pages, tutorials, expectations and evidence, and list the gaps. plan --coverage covers the model, not the product.
  • Don’t run a journey that trades, pays, posts or creates accounts until you know what it changes, where it goes and what isolates it. See Safety preflight.
  • Don’t capture what you can’t share. Screenshots, accessibility trees, logs and HARs can hold recovery phrases, keys, credentials and account data. Check what is captured, what redacts it, and where the results and manual end up. See Evidence privacy.
  • A command that exits 0 hasn’t verified anything by itself. Unbound steps are “not supported yet”, not failures, so a run with nothing bound passes, and a failed screenshot is a warning. Read the per-plan results and check that the stories and screenshots you expect are there. See Remote drivers.
  • Audit with a reader who lacks your context, and say for each claim whether it was observed, simulated, only read in the source, or not shown at all.
  • Report three verdicts separately: the specification, the tests, and approval. “Not supported yet” is not “passing”, a passing test does not approve the prose, and Approval: is separate from both Status: pending and the test results. See Reporting.
  • A manual of just the agreed behaviour: expectation docs <dir> <out> --approved-only. It keeps only what is marked Approval: approved; unmarked counts as not approved, so on a suite that doesn’t mark approval it writes an empty manual. Check the suite first.

Getting started

This chapter runs a complete suite against a tiny system: a coin-operated turnstile. It’s the turnstile example in the repository.

Add the crates

Expectation isn’t on crates.io yet. Depend on the git repository:

[dev-dependencies]
expectation_harness = { git = "https://github.com/ptescher/expectation" }
expectation_story = { git = "https://github.com/ptescher/expectation" }

For the command-line tool:

cargo install --git https://github.com/ptescher/expectation expectation_cli

That installs a binary called expectation. For a build you can repeat, pin the commit: see Pinning a version.

If your product isn’t written in Rust, read Getting started without Rust instead: the suite is the same, and the driver is JavaScript.

Write the suite

A suite is every *.expect file under a directory. Make expectations/turnstile.expect (expectation init writes a commented one much like it):

Suite: Turnstile

Vocabulary:
  State: the turnstile is locked | unlocked
  State: the coin box has 0..1000 coins
  Event: a visitor inserts a coin
  Event: a visitor pushes the arm

Background:
  Given the turnstile is locked
  And the coin box has 0 coins

Feature: Paying to go through
  Expectation: A coin unlocks it
    Given the turnstile is locked
    When a visitor inserts a coin
    Then the turnstile is unlocked
    And the coin box goes up by 1

  Expectation: Pushing through locks it again
    Given the turnstile is unlocked
    When a visitor pushes the arm
    Then the turnstile is locked

  Expectation: Pushing a locked turnstile does nothing
    Given the turnstile is locked
    When a visitor pushes the arm
    Then the turnstile is locked

Story: A day at the zoo
  As a visitor
  I want to pay once and go through
  So that I can see the animals

  When a visitor inserts a coin
  Then the turnstile is unlocked
  When a visitor pushes the arm
  Then the turnstile is locked
  • The vocabulary declares the states the system can be in, and the events that can happen. Every other line must use these words.
  • The Background is the state every test starts from.
  • Expectations are the rules. goes up by 1 is a relative Then: it checks the change, whatever the count was.
  • The story is a journey through them.

Nothing ran, but the suite was checked: every step uses the vocabulary, no two expectations disagree, and the story only relies on behaviour the expectations specify. The first warning says one expectation has no story, and how a story could reach it. The second is about the manual: the story becomes a tutorial, and two steps make a thin one. A suite this small can live with both.

“Search truncated” is normal here: every coin makes a new state, so the search for what leads to what stops at its depth limit instead of counting to 1000. It has already found everything by then.

Try breaking it. Add a fourth expectation:

  Expectation: A hard push forces it
    Given the turnstile is locked
    When a visitor pushes the arm
    Then the turnstile is unlocked

check now fails. Both this and «Pushing a locked turnstile does nothing» apply when a visitor pushes a locked turnstile, and they disagree about the turnstile. The error names that situation and suggests settling it with Overrides: if one is an exception to the other. Here neither is, so take the new one out again.

Bind it to the system

The runner talks to the system through a driver. Bindings builds one from closures, one per vocabulary term:

#![allow(unused)]
fn main() {
use expectation_harness::{Acceptance, Bindings, RunOptions};

#[derive(Default)]
struct Turnstile {
    locked: bool,
    coins: u32,
}

#[test]
fn turnstile_behaves() {
    let mut driver = Bindings::new(Turnstile { locked: true, coins: 0 })
        .observe("the turnstile", |t| if t.locked { "locked" } else { "unlocked" })
        .observe("the coin box", |t| t.coins as f64)
        .arrange("the turnstile", |t, v| t.locked = v.as_str() == Some("locked"))
        .arrange("the coin box", |t, v| t.coins = v.as_f64().unwrap() as u32)
        .on("a visitor inserts a coin", |t| {
            t.coins += 1;
            t.locked = false;
        })
        .on("a visitor pushes the arm", |t| t.locked = true)
        .on_reset(|t| *t = Turnstile { locked: true, coins: 0 });

    Acceptance::load("expectations")
        .unwrap_or_else(|e| panic!("{e}"))
        .with_coverage()
        .assert_passes(&mut driver, &RunOptions::default());
}
}
  • observe reads a state back. Named values are strings; numbers are f64.
  • arrange puts a state in place before a test starts (the Background, a scenario’s Givens).
  • on makes an event happen.
  • on_reset runs before every test.

with_coverage() adds a generated test for each expectation no story reaches, so all three are verified. assert_passes panics with every failing check if anything fails.

Write the docs

Pass a docs_dir to take screenshots (if the driver has on_screenshot), then write the manual:

#![allow(unused)]
fn main() {
let acceptance = Acceptance::load("expectations")?.with_coverage();
let opts = RunOptions { docs_dir: Some("docs".into()), ..Default::default() };
let report = acceptance.run(&mut driver, &opts);
acceptance.docs(Some(&report)).write("docs")?;
}

docs/README.md is the manual in Markdown, and docs/site/index.html is the same as a website. The story is now a tutorial called “A day at the zoo”.

Getting started without Rust

Getting started runs a suite from a Rust test. If your product is JavaScript or TypeScript, you don’t write any Rust: the suite is the same .expect files, the driver is a JavaScript object, and a command called expectation-run runs the tests through it. This chapter is the cart-node example in the repository.

Install the commands

The two commands are built from source, so this step needs a Rust toolchain once. Nothing in your project depends on it afterwards.

cargo install --git https://github.com/ptescher/expectation expectation_cli      # expectation
cargo install --git https://github.com/ptescher/expectation expectation_remote   # expectation-run

For a build you can repeat, pin the commit: see Pinning a version.

The JavaScript client is not on npm yet. It is two files with no dependencies, in clients/js: copy them into your project (say vendor/expectation-driver/), or add the repository as a git submodule, and depend on that directory:

{ "devDependencies": { "expectation-driver": "file:vendor/expectation-driver" } }

Write the driver

The driver has one handler for each word of the vocabulary. The state’s subject (“the cart”, “the checkout”) names it; an event is named in full.

// driver.mjs
import { ExpectationDriver } from 'expectation-driver';
import { Cart } from './cart.js';

export function cartDriver() {
  let cart = new Cart();
  return new ExpectationDriver({ platform: 'node', app: 'Cart' })
    // observe: read a state back. A named value is a string, a number is a number.
    .observe('the cart', () => cart.items.length)
    .observe('the checkout', () => cart.checkout)
    // arrange: put a state in place before a test starts, however is quickest.
    .arrange('the cart', n => { cart.items = Array.from({ length: n }, (_, i) => `item ${i + 1}`); })
    .arrange('the checkout', v => { cart.checkout = v; })
    // on: make an event happen.
    .on('the shopper adds an item', () => cart.add('tea'))
    .on('the shopper opens the checkout', () => cart.openCheckout())
    .on('the shopper pays', () => cart.pay())
    // reset: runs before each test.
    .onReset(() => { cart = new Cart(); });
}

Handlers may be async. A word with no handler is not an error: tests that need it are reported as “not supported yet”, so you can bind a suite a word at a time.

Run it

Two processes take part. expectation-run reads the suite and listens on a port. The driver connects out to it, and the runner sends it one command at a time: reset, arrange this, make that happen, what is the cart now. The simplest arrangement is a script that starts both:

// run.mjs
import { spawn } from 'node:child_process';
import { cartDriver } from './driver.mjs';

const addr = '127.0.0.1:4477';
const runner = spawn('expectation-run', [
  'expectations',
  '--addr', addr,
  '--docs', 'docs',       // save the results and write the manual here
  '--runner', 'node',     // the name these results are saved under
  '--settle', '0',        // this cart answers at once; a UI needs time after each action
  '--strict',             // every test must run and pass
], { stdio: 'inherit' });

const driver = cartDriver();
driver.start(`http://${addr}`);

runner.on('exit', code => {
  driver.stop();
  process.exit(code ?? 1);
});

node run.mjs

waiting for an app at http://127.0.0.1:4477 ...
Cart (node) connected
✓ Buy two things
✓ Reaching «An empty cart has nothing to check out»
docs: /path/to/your/project/docs/README.md

The second test is a generated one: no story reaches that expectation, so the runner wrote a test that does. docs/README.md is the manual in Markdown, and docs/site/index.html is the same as a website, with “Buy two things” as a tutorial.

Read the lines, not just the exit code: ✓ passed, ✗ failed and – is anything else (not supported yet, pending, not run). Without --strict a run where nothing was bound exits 0.

A web app: the same driver, through the browser

For a web app, keep everything above and change what the handlers do. They run in your test process and act on the page through a browser automation library, so an event is a real click and an observation is what the page shows. With Playwright:

import { chromium } from 'playwright';
import { ExpectationDriver } from 'expectation-driver';

const browser = await chromium.launch();
let page = await browser.newPage();

const driver = new ExpectationDriver({ platform: 'web', app: 'Shop' })
  .observe('the cart', async () => Number(await page.getByTestId('cart-badge').innerText()))
  .observe('the checkout', async () =>
    (await page.getByText('Thanks for your order').isVisible()) ? 'paid'
      : (await page.getByTestId('payment-form').isVisible()) ? 'open' : 'closed')
  .on('the shopper adds an item', () => page.getByRole('button', { name: 'Add to cart' }).first().click())
  .on('the shopper opens the checkout', () => page.getByRole('button', { name: 'Checkout' }).click())
  .on('the shopper pays', async () => {
    await page.getByLabel('Card number').fill('4242 4242 4242 4242');
    await page.getByRole('button', { name: 'Pay' }).click();
  })
  .onReset(async () => {
    await page.context().clearCookies();
    await page.goto('http://localhost:3000');
  })
  .onScreenshot(async () => (await page.screenshot()).toString('base64'));

This sketch is not one of the repository’s tested examples: the selectors are your app’s. Three things differ from the embedded driver:

  • arrange needs a way in. The Background here is the empty cart that onReset gives, so nothing is arranged. A generated test that starts from another state needs arrange handlers, and from outside the app those have to use a UI path, a seeded database or a test endpoint. Without them such a test is “not supported yet”.
  • Give the page time. Leave --settle at its default (one second) or set it to what your app needs; the runner also keeps looking until every check holds or its patience runs out.
  • Screenshots come for free. With onScreenshot, every step of every tutorial in the manual has a picture.

Start your app’s dev server before the run, or let the suite say how with a Launch: line (see The language). Before a suite drives anything that pays, posts or sends, read Safety preflight.

Remote drivers has the rest: the Swift client, what an embedded driver shows and what an external one shows, and the protocol, which any language that can make an HTTP request can speak.

Spec first: a feature before it is built

Most of this guide describes a product that exists. This chapter is the other direction: the suite says what a feature will do, someone agrees to it, and then it is built until the tests pass. It suits a team where a person decides the behaviour and an AI agent, or another developer, writes the code.

Three markers keep the three questions apart, and none of them stands in for another:

QuestionMarkerWho changes it
Is the behaviour agreed?Approval: proposed, then approvedThe person who owns the decision
Is it built?Status: pending, then removedWhoever builds it
Does it work?The run’s resultThe run

1. Write what it will do

Add the feature to the suite as if it existed: its words in the vocabulary, a description for the reader, its expectations and a story. Mark the feature and its story Approval: proposed, and each expectation that isn’t built Status: pending.

This adds a way to take an item out of the cart example:

Vocabulary:
  Event: the shopper removes an item
    Say: press Remove next to the item

Feature: Changing your mind
  Approval: proposed

  You can take an item out of the cart again before you pay.

  Expectation: Removing an item takes it out of the cart
    Status: pending
    Given the checkout is closed
    And the cart has at least 1 item
    When the shopper removes an item
    Then the cart goes down by 1

Story: Take one back out
  Approval: proposed
  As a shopper
  I want to remove something I added by mistake
  So that I only pay for what I want

  When the shopper adds an item
  Then the cart has 1 item
  When the shopper adds an item
  Then the cart has 2 items
  When the shopper removes an item
  Then the cart has 1 item

Where the behaviour is not decided, don’t pick an answer. Write the question in the description, starting with the word Unresolved: so it is easy to find, and ask. Unresolved: is not a keyword: it is ordinary description text, and the manual prints it as written.

2. Check it against what is already there

expectation check expectations
expectation plan expectations --coverage

A pending expectation is part of the model, so this is where the new feature meets the old ones, before any code exists:

  • A conflict means the new behaviour and an existing one both apply somewhere and promise different things. That is a product question: one is an exception (Overrides:), or a Given is too wide.
  • unspecified or unclear-step on the story means it leans on behaviour nobody wrote down.
  • unreachable means nothing gets the product into the state the feature starts from.

plan prints the test each story will become. Read it: it is what “done” will mean.

3. Get it agreed

Generate the manual and give the feature’s page and its tutorial to whoever decides:

expectation docs expectations docs

They read prose and numbered steps, not Gherkin. When they agree, they (or you, on their word) change Approval: proposed to Approval: approved. An agent does not approve its own specification. A suite can keep drafts and agreed behaviour side by side; expectation docs expectations out --approved-only writes the agreed part alone.

4. Build it

Now write the code, and bind the new words in the driver (.on("the shopper removes an item", …)). While the expectation is pending, a test that depends on it is not run, and a run reports it apart from the rest:

✓ Buy two things
– Take one back out
✓ Reaching «An empty cart has nothing to check out»

The run exits 0: – is “pending”, not “passed”. Tests of everything else still run, so the suite keeps catching what the new code breaks.

5. Take the pending mark off

When the behaviour is built, delete its Status: pending line and run again. The story is now a real test. It passes, or it fails with the check that didn’t hold, or it is “not supported yet” because the driver doesn’t bind a word it needs.

6. Gate on it

A plain run passes when nothing failed, which is right while a feature is under way and wrong for a release. Ask for more with a policy (see A run as a gate):

WhenRun withPasses when
Every pull requestthe defaultnothing failed
Before merging a finished feature--strict (Policy::Required)every test that isn’t pending ran and passed
Before a release--strict=all (Policy::All)every test ran and passed, and nothing is pending

With the pending story above, --strict exits 0 and --strict=all exits 1:

Not every test ran and passed (--strict):
– pending: Take one back out (Pending: it depends on «Removing an item takes it out of the cart», which isn't built yet.)

In CI has a workflow that does this.

For an agent building the feature

  • The specification is the task. Don’t change an approved expectation to make a test pass; if the specification is wrong, say so and ask.
  • Remove Status: pending only for behaviour you built in this change, and run the suite after you do.
  • A word the driver doesn’t bind makes a test “not supported yet”, which a default run lets by. Bind it, or say plainly that it isn’t bound.
  • Report what the run showed, test by test: passed, failed, pending, not supported yet. An exit code of 0 is not that report.

A worked example: the kettle

The kettle example is a suite of five files about an electric kettle, run against a toy kettle with time in it. This chapter walks through it: the vocabulary, a conflict and its exception, stories, generated coverage, a failing run, and the manual it writes.

cargo run -p expectation_harness --example kettle

The manual it writes is published here: the kettle manual.

The vocabulary

vocabulary.expect declares every word the suite may use, how the manual words it, and where every test starts (shortened here):

Vocabulary:
  State: the kettle is off | starting | heating | dry
    Shows: off: the display reads OFF and the light is grey
    Shows: heating: the display reads HEATING, the light is red and steam rises
    Shows: dry: the display reads DRY in red and says "Refill, then press reset"
  State: the dial is 0..100 %
    Set: turn the dial to {value}
  State: the preset is WARM | HOT | BOIL
    Shows: the PRESET line reads {value}
  State: the child lock is on | off
  Event: the user presses start
    Say: press START
  Event: the user presses reset
  Event: the user presses preset
  Event: the user presses lock
  # A sensor, not something the user does: the tests make it happen.
  Event: the water runs out
    Say: the kettle boils dry

  Phrase: the kettle is plugged in and full
    Say: fill the kettle and plug it in
    Given the kettle is off
    And the dial is 0 %
    And the preset is WARM
    And the child lock is off

Background:
  Given the kettle is plugged in and full

The dial is a number, so steps can compare it: above 55 %, between 20 and 40 %. The others have named values. Say:, Set: and Shows: are what the manual tells the reader to do and what they will see. “The water runs out” is an event without a person, so its Say: describes what happens rather than telling the reader to do it. The phrase makes “Before you begin” one line.

Features and an exception

heating.expect says how the kettle starts and stops:

Feature: Heating

The driver

world.rs is the toy kettle. Like a real one, it takes time: the dial has to stay above 55 % for 0.6 s before the kettle starts, and starting takes another 0.22 s. The driver binds each term and says how time passes:

#![allow(unused)]
fn main() {
Bindings::new(World::new(lock_leaks))
    .observe("the kettle", |w| w.phase_name())
    .observe("the dial", |w| w.dial)
    .set("the dial", |w, v| w.dial = v.as_f64().unwrap())
    .arrange("the kettle", |w, v| /* put it in that phase */)
    .on("the user presses lock", World::press_lock)
    // ...
    .on_settle(|w| (0..20).for_each(|_| w.tick(0.05)))   // a second after each action
    .on_advance(|w| { w.tick(0.1); Progress::Advanced }) // then 0.1 s per extra look
    .on_screenshot(|w| Screenshot::svg(w.svg()))
}

Settling a full second after each action is what makes “Then the kettle is off” mean it stays off, not that it was off for the instant before it switched on. See Drivers.

Suites and sections

An optional Suite: <name> line names the suite. Otherwise it’s named after its directory.

Each directory under the suite is a section: a nested set of features that share a setup. Its Section: <name> line (in any of its files) and the text under it name and describe it. A leading 01- in a directory name only sets the order.

A section’s Background: is its setup, written over its parent’s. So everything in app/drawing/ starts where app/ does, with the pen picked on top. Pages about a section start from that setup and don’t re-explain how to get there, the way a manual assumes you’ve read the chapter before.

A setup is a state the tests can arrange the system in, written as Givens: a section’s Background, or a phrase made only of Givens. Follows: and Hands over to: name one.

A section’s Launch: line, right under its Section: line, says how to start the program under test: Launch: run cargo run -p kettle. It is always shown first under “Before you begin” and never as a numbered step, every sub-section inherits it, and a sub-section’s own Launch: replaces it (Launch[iOS]: for another platform). Drivers get it as Driver::launch, called once for the tests that share it, so a runner doesn’t start its own server. A Say: that holds a shell command in backticks (one that starts with a program name or a path, like `cargo run` or `./app`) gets a launch-in-step warning.

Each top-level section is a system of its own: stories and the flow graph only use the expectations in their own top-level section.

Vocabulary

LineDeclares
State: <subject> is <a> | <b> | …A state with named values.
State: <subject> is <min>..<max> [unit]A number, optionally with a unit.
Event: <phrase>Something that happens.
Phrase: <name>A step of your own, made of other steps.
Term: <name>A word for the glossary, defined by the text under it.
Reference: <label> | <url>In a Term: a link to outside documentation.

A state can use are, has or have instead of is (“the drawing has 0..650 shapes”), and steps about it read the same way. The subject can hold one of those words itself: in State: the page that has focus is home | settings the subject is “the page that has focus”, because the verb that counts is the last one before the first value.

A state with named values has 2 to 64 of them. A value can’t contain or, which steps use to list values. It can start with not (“the job is not started | running | done”), and the job is not started then names it, unless started is a value too, which is an error because the step could mean either.

A number’s range can use decimals and negative numbers (-20..40 °C), and its minimum must be below its maximum.

Vocabularies from all files merge into one, by name, so a section can declare the words only it uses.

Scoping the words of a large suite

In a big suite with several teams, merging by name means two sections that each declare “the user is signed in” quietly get one state, and expectation check warns about it (vocabulary-collision). To give each top-level section its own words, say so once in a Vocabulary block in the suite’s top directory:

Vocabulary:
  Scopes: sections
  # Shared, because it is declared in the top directory:
  State: the user is signed in | out

Then:

  • Words declared in a file under a top-level section (billing/, search/, …) belong to that section and the sections inside it. Two sections can declare “the invoice is open | paid” and “the invoice is 0..5” without meeting.
  • Words declared in the top directory are shared, and every section can use them.
  • A section can’t declare a word that is also shared (vocabulary-shadow), and a step can’t use another section’s word (it is an unknown step).
  • Two sections that declare the same state the same way get a duplicate-word warning: if it is one word, move it to the top directory. A section’s own word counts as used only by its own steps.
  • Stories and the flow graph already stay within a top-level section, so nothing else changes.

A suite without Scopes: behaves as before.

How the docs say things

Name events for what the user means, not the button they press: “the user starts the kettle”, not “the user presses START”. The button goes in lines under the declaration:

LineUnderSays
Say: <instruction>an event or phraseWhat the docs tell the reader to do: “Press START.”
Set: <instruction with {value}>a stateHow to change it: “press PRESET until the display reads {value}”.
Set: <value>: <instruction>a state with named valuesHow to change it to that value: Set: lost: switch off the radio.
Shows: <value>: <what you see>a stateWhat the reader sees when it has that value: Shows: dry: the display says DRY.
Shows: <text with {value}>a stateThe same for any exact value: Shows: the counter reads {value} SHAPES.

For a number, a Shows: can start with a comparison in any form a step accepts (see Steps): at least 99 %:, over 50 %:. A Shows: can also start with a change, as a relative Then writes it: goes up by 1:.

Without these, the docs make do. “The user clicks the canvas” becomes “Click the canvas”, “the water runs out” becomes “Wait until the water runs out”, and a state becomes “Set the dial to 80 %”.

Phrases

A phrase is a step of your own, for saying more with less.

  • A phrase of Givens is a setup (“the kettle is plugged in and full”). Use it in a Background, a Given, or at the start of a scenario.
  • A phrase of Whens is a sequence of actions (“the user draws two shapes”, one When per action). An expectation can use one that’s a single action; a story step can use any. It becomes several test steps, but stays one numbered step in the docs.

A phrase can’t mix Givens and Whens (bad-phrase). Its Say: is how the docs put it. A phrase can use any other phrase, wherever in the suite that one is written; two that use each other are an error.

Steps

A step is an event, a phrase, or a fact <subject> is [not] <predicate>.

The negative forms are is not, are not, isn't, aren't, doesn't have and don't have.

For a state with named values, the predicate is one or more values: off, off or heating, not dry.

For a number, the predicate is the number itself or a comparison:

WriteMeans
80 %exactly 80
above 55 %, over, more than, greater than, higher thanmore than 55, not 55 itself
below 10, under, less than, fewer than, lower thanless than 10, not 10 itself
at least 2020 or more
at most 4040 or less
between 20 and 40 %20 to 40, both included

The unit is optional. A number can’t be negated: write below 5 or above 5, not not 5.

Matching ignores case, extra spaces, a full stop at the end and a leading “the”, “a” or “an”. A unit matches its plural, so “1 shape” matches a unit of “shapes”. A unit of one letter has no plural: with a unit of ms, 5 m is an error. A step outside the vocabulary is an error, with a “did you mean” hint.

An expectation’s Then can also be relative: the drawing goes up by 1, goes down by 10 m (for numbers), or stays the same (for any state). Relative steps only go in an expectation’s Then (misplaced-shift).

Expectations

Expectation: <name>
  Approval: approved | proposed
  On: <platform>, …
  Status: pending
  Docs: hidden
  Overrides: <another expectation>
  Hands over to: <a setup>
  <description>
  Given …
  When …
  Then …

Every line but the name and a Then is optional.

  • Given is the state before. Several are joined with And (or But).
  • When is at most one event, plus any states the outside world changes (such as the dial). Several When lines make one action, so two events need two expectations (two-events).
  • Then is the state after. States the Then doesn’t mention keep their values.
  • The steps go Given, When, Then, in that order, and can’t start with And or But.
  • An expectation with no When is an invariant: it holds whenever its Given does.
  • Docs: hidden keeps it off its topic page. It’s still tested, and it’s in the test report; links to it from the maps and test pages go to a test that covers it.
  • Approval: says whether the specification itself is agreed. See Approval.
  • On: limits it to some platforms. See Platforms.

Text before the first step is the expectation’s description. A line there that starts with Given, When, Then, And or But is a step, so start description sentences with another word.

Exceptions

Overrides: <name> makes an expectation an exception to another: where both apply, this one wins. An expectation can override several, one line each, and overrides must form a DAG (override-cycle).

Handing over to another program

Hands over to: <setup> says that when the expectation fires, a different program (or part of one) takes over, and it starts in that setup: the launcher starts the sim, so afterwards the sim is “just started”.

A section whose Background is that setup is then reached from here instead of being a start of the state map. The state map goes on from the setup alone (the launcher’s buttons say nothing about the sim). Stories and tests don’t see the hand-over: they stay in the launcher, and check the expectation’s Then.

Written before it is built

Status: pending says the behaviour is written ahead of its implementation. A pending expectation stays in the model: it appears in the map and the state map, it can be reached, and conflicts with it (pending or required) are still errors.

What changes is testing. A test that depends on it, because it fires it or because it is an invariant in force there, is not run. The report shows that test as pending, which is neither passed, failed nor “not supported yet” (that one means the driver lacks a binding, and is still reported as such for everything else). Pending tests don’t fail the run and never count as verified, and the expectation’s own verdict is pending. Failures in the other tests still fail the run.

Remove the line when the behaviour is built. Because an invariant applies wherever its Given holds, a pending invariant makes the tests in its section pending, so prefer pending transitions.

Approval

Approval: approved or Approval: proposed goes right under a Feature:, Expectation: or Story: line (before its description or steps), once, and says whether the specification itself has been agreed. It is for teams that keep drafts and agreed behaviour in one suite, and it changes nothing about checking, planning or running.

  • An expectation without its own Approval: has its feature’s. Nothing says it, and unmarked counts as not approved when an approved-only manual is asked for (see the manual).
  • An approved expectation inside a proposed feature is an error (approval-conflict).
  • It is separate from Status: pending. A pending expectation is agreed but not built; a proposed one may be built and passing but is not agreed.

Backgrounds that follow a setup

A section’s Background can say which setup it is reached from:

Background:
  Follows: the launcher has just opened
  Given the station is connected to the TX15
  And the other plane is silent

The section is reached from that setup, not a start of the state map: only the setup that nothing leads to is. Its “Before you begin” starts from the section whose setup it follows.

How it’s reached depends on whether the expectations can say:

  • They can. Where a chain of expectations gets from the followed setup to this one (a website’s home page has a link to billing), that chain is the way in. The state map shows its real moves, and the docs give its steps. With coverage on, a generated test “Reaching «Billing»” arranges the followed setup, takes the route and checks everything the section’s setup says. The section’s own tests arrange its setup directly (a deep link), so this is the test that shows the way in gets to the same place.
  • They change every state the setup needs, but nothing gets there. That’s an error (follows-no-way-in): the route it claims is broken. Changing the link so it goes somewhere else gives you this error.
  • Some state the setup needs, nothing changes (the station is connected to the TX15). The Background’s steps (and their Say:) are what you do, and the state map has one move from the followed setup to the section, named by the section. That move is a claim about how to set up, which nothing tests.

If nothing gets to the setup a section follows, that’s a follows-unreached warning. Hands over to: is the same idea for what a tested expectation does.

  • The narrative is the lines that start with “As a”, “As an”, “I want”, “So that” or “In order to”, and a line that starts with “As” when the next one starts with “I want” (“As someone who drinks green tea”).
  • Any other text is the introduction, which opens the tutorial in the docs. Before the first Scenario: it is all introduction, even a sentence that starts with “When”.
  • A story has one or more Scenario:s. A story with none can have its steps straight under it, and they form a single scenario; in such a story the first line that starts with a step keyword ends the introduction.

  • After that, each When starts a step, And/But add to it, and its Thens are what the story checks afterwards.

Links and the glossary

Term: <name> and the text under it define a word for the glossary. Any text can link to a term, a section, a feature, an expectation or a story with [[its name]], and mark code with backticks.

A term can point to documentation outside the suite with a Reference: line, either Reference: <label> | <url> or just Reference: <url>. The glossary shows it as a link under the definition, using the label when there is one. The term keeps its own name and anchor, so the label can be a different name for the same thing, such as an API schema:

Term: Account
  The customer's account within this domain.
  Reference: AccountResponse | https://api.example.com/docs/models/AccountResponse

Only http and https URLs are accepted, without spaces, quotes or angle brackets. A term has at most one reference, and it is documentation only: it changes nothing in the vocabulary or the tests.

Platforms

One suite can describe a system that exists on several platforms: a desktop app and a phone app that do the same job, say. Everything written plainly is true on every platform. Where one differs, the suite says so, and each platform reads the suite as its own.

Vocabulary:
  # The first is the default: plain lines are about it.
  Platform: desktop | iOS

  Event: the user unlocks the door
    Say: press UNLOCK
    # How the docs tell an iOS reader to do it:
    Say[iOS]: tap UNLOCK
  State: the door is locked | unlocked
    # Replaces the plain Shows lines:
    Shows[iOS]: unlocked: the UNLOCKED badge turns green

  Phrase: the app is open on a new account
    Given the tool is pan
  Phrase[iOS]: the app is open on a new account
    # A start that iOS can reach:
    Given the user is signed in

Section: Drawing
  # Also under a Feature, Expectation or Story:
  On: desktop

The rules

  • Platform: <a> | <b> | … declares the platforms. The first is the default.
  • Say[P]:, Set[P]: and Shows[P]: replace the plain line for platform P.
  • Phrase[P]: replaces the plain phrase of the same name for P.
  • On: desktop, iOS says that the section (the whole directory), feature, expectation or story is only about those platforms. Use it for what a platform doesn’t have. An exception to an expectation that isn’t on a platform is dropped there.
  • Tag only the platforms that differ from the default. Tagging the default is an error (default-platform), and so is a name that isn’t declared (unknown-platform).

Checking, running and docs

expectation check checks the suite as each platform reads it, and every one must check clean.

A driver reads the suite for its platform and runs its tests:

#![allow(unused)]
fn main() {
let acceptance = Acceptance::load_for("expectations", "iOS")?;
}

Its results are its own (results/app@iOS.tsv), apart from those of runners that are the same everywhere (api.tsv). Acceptance::publish(dir, runner, &report) saves a run’s results and merges them with what other runners saved.

expectation docs writes one manual per platform: the default at the root and the others under platforms/<name>/. Every HTML page has a Platform menu that opens the same page in the other manual.

The platforms share one docs directory, and so one screenshots/. The default platform’s are in screenshots/<test>/, and each other platform’s in a folder of its own, screenshots/platforms/<name>/<test>/, so the same test on two platforms never shows the other’s picture. expectation-run --docs does this. A driver in Rust gets it from acceptance.run_options("docs"), or by setting RunOptions::screenshots_under to acceptance.screenshots_under():

#![allow(unused)]
fn main() {
let acceptance = Acceptance::load_for("expectations", "iOS")?;
let report = acceptance.run(&mut driver, &acceptance.run_options("docs"));
acceptance.publish("docs".as_ref(), "app", &report)?;
}

Results saved before this name a later platform’s screenshots as screenshots/<test>/…. Its manual shows a placeholder for those until the tests run again. Screenshots kept by content in a store are the same on every platform.

Writing specs that read well

For how deep a feature description should go, with an example that has an outside service, an unavailable state and an open decision, see Feature docs that explain. For lists, records and typed-in text, see Modelling an app with data.

The generated manual is only as good as the words in the specs. A suite that tests well but reads badly is half done: the same lines are the user’s documentation. This is a loop that works.

1. Start from what the user does

Write a handful of high-level expectations in the user’s words, before any detail. Name states for what the user sees (“the kettle is heating”), not for internals (“the relay is closed”). Name events for what the user means (“the user starts the kettle”), not for the control (“the user presses START”). The control goes in a Say:.

2. Let the checker shape the model

expectation check expectations
expectation graph expectations > flow.mmd
  • A conflict is a question the spec hasn’t answered. Decide which behaviour wins, and say so with Overrides:, or narrow a Given so they can’t both apply.
  • An unreachable expectation means nothing gets the system into its Given. Add the expectation that does, or fix the Background.
  • No way in means a section’s setup can’t be reached from its parent’s. The docs need that route to say “Before you begin”.

3. Write stories as tutorials

One goal per story, in the order a new user meets things. The narrative says who and why. The introduction is the tutorial’s first paragraph: the situation, how the feature works and how to read what the reader will see. A story follows the path a user with that goal would take, not a sequence that exercises states; that is what expectations and generated tests are for. A story’s Thens are what the reader should notice, not everything that’s true; the expectations already check the rest. What a story needs has the full checklist.

expectation plan expectations

shows each story as the test it compiles to, and errors when a story leans on behaviour the expectations don’t promise.

4. Give the docs words

Add Say: to events and phrases, Set: to states the reader changes, and Shows: to states the reader sees. Turn long setups into phrases (“the kettle is plugged in and full”), so “Before you begin” is one line, not a list of states. Define jargon with Term:.

5. Generate and read as a newcomer

expectation docs expectations docs

Read docs/README.md and the site as someone who has never seen the system. Better: have someone else do it, or ask an AI agent to audit the pages as a reader and list what’s vague, missing or confusing.

6. Fix the specs, then loop

For each finding, change the spec, not the generated page:

FindingFix
A vague stepa better Say:, a phrase, or a Then
A missing whya description under the feature or expectation
A confusing titlea better name
A state dump in “Before you begin”a setup phrase with a Say:
A word the reader doesn’t knowa Term:

Then check, regenerate and read again, until the docs read well.

Style

Keep reader-facing text short and plain. Simplified Technical English (ASD-STE100) is a good target: one instruction per sentence, active voice, present tense, common words, no more than about 20 words a sentence. The docs generator already writes instructions this way, so specs in the same style blend in.

Feature docs that explain

A suite can pass every check and still make a thin manual. The usual cause is a description that lists test conditions and caveats and never says what the feature is for. This chapter is the depth to aim for, a workflow to get there, how to audit the result, and a worked example you can run:

expectation check examples/smart-kettle
expectation docs examples/smart-kettle docs

The example is examples/smart-kettle: a smart kettle that shows the electricity price from an outside provider and boils when the price is cheap. It has a feature that depends on an outside service, a state for when that service is unavailable, and a decision nobody has made yet. The manuals it generates are published: with its drafts and approved only. If you are an AI agent, there is a skill with this chapter’s checklist.

What a feature page needs

The text under Feature: is the first thing a reader sees. Write it for someone who has never talked to you. For each user-facing feature, cover:

  1. What it does, who uses it, and what it helps them decide or do. One or two sentences, in the user’s words (“someone who makes tea every morning”).
  2. The normal workflow. What the user does, what goes in, what comes out.
  3. How to read the result. What a dot, a number, a banner or an empty list means, and what to do about it.
  4. The states that are not the happy path. Empty, unavailable, invalid, partial, late; and any limit that matters, like “one cheap rate per boil”.
  5. What is settled and what is not. Say what is agreed. If something is undecided, write Unresolved: and the question, and mark the expectation Approval: proposed. Do not invent an answer to make the page read smoothly; ask for the decision. (Unresolved: is ordinary description text that is easy to search for, not a keyword.)
  6. The promises the tests check. These are the Expectation:s under the description.

Leave filler out, not context. A paragraph per point is normal. A description that a reader could not follow without having sat in the planning meeting is too thin, however short.

Each expectation can have a description too. Use it for the why of one rule (“A number that might be hours old is worse than none”).

What a story needs

A story becomes a tutorial: the page a reader follows to get something done. It has to teach the feature, not replay a test. A test needs steps that reach each state; a reader needs to know why they are there, what they are looking at and what it means. For each story, cover:

  1. A real goal, and where the reader starts. The narrative (As a … I want … So that …) is the reader’s reason. The introduction says the situation, what they want to do or find out, and where in the product they begin: “You hold USDC and want to know who else holds it”, not “Toggle the currency”.
  2. The path someone with that goal would take. Steps in the order a user would do them, ending when the goal is met. Reaching every state and transition is the expectations’ job, and plan --coverage generates tests for the ones no story reaches. A story that flips a toggle back and forth to exercise it is a test sequence, not a tutorial.
  3. How it works. The mechanism the reader relies on: where the data comes from, what the product does for them and what it does not, why a result can be late or missing. Say it in the introduction and link the feature and terms ([[Price provider]]) that say more.
  4. How to read what they see. Units (SOL or dollars, per token or total), what a row, number, dot or badge means, and what to do next. The Shows: of each state is what a step says the reader sees; make it something they can check, and explain in the introduction or the linked feature what it tells them.
  5. What goes wrong along the way. The empty, late or failed case a user is likely to meet on this journey, and what to do about it, as the kettle’s main story does when the provider goes quiet.
  6. Where they end up. The last step reaches the goal, worded as the reader sees it. A story’s Thens are what the reader should notice, not everything that is true; the expectations check the rest.

Together, a feature’s page and its stories explain the whole feature: each main goal it serves has a story. The test for a story: could someone who has never seen the product follow the tutorial on its own, and afterwards explain the feature to someone else? If they could only repeat the taps, it is too thin.

The product story, not the test rig

The main prose is the product as a user meets it: they sign in with Google, the provider goes quiet, the price reaches their rate. It is not the mock OIDC server, the fixture account or the switch a test flips. Put the machinery where contributors look for it: the driver, a comment in the vocabulary, the test report or contributor docs. In the vocabulary, a Say: for something the user does not cause describes what happens (“the price provider stops answering”), not how a test makes it happen (“switch the test provider off”).

Moving the machinery out of the story does not hide what it means. If a caveat changes what a reader can conclude, keep it on the page in plain words: “the sign-in tests use a stand-in provider, so they do not show that Google or Apple sign-in works”. A caveat about how a test is built belongs with the test; a caveat about what the product has been shown to do belongs with the claim.

The workflow

This is for a product that exists. For a feature that isn’t built yet, start from Spec first and come back here for the depth of the pages.

  1. Look at the product first. Read the code, the UI, existing docs, tickets and the people who know it. Note what you can see and what you are assuming.
  2. Inventory the user goals. List what people use the product to do (buy a token, find a holder, follow a wallet, sign in), from the product, not from the suite you are about to write. This is the coverage map; keep it up to date as you go.
  3. Write the explanation and the expectations together. The description, the vocabulary’s Say:/Set:/Shows:, the expectations and one story per user goal. A description written afterwards drifts from what is tested.
  4. Check. expectation check <dir> must pass. Fix every error; read every warning.
  5. Plan with coverage. expectation plan <dir> --coverage shows the tests each story becomes and the generated ones for expectations no story reaches. Add a story, or accept a generated test, for each untested warning. This is coverage of the model: it says nothing about goals the suite never mentions.
  6. Preflight anything that changes state, then run. Before you run a journey that trades, pays, posts, follows, notifies or creates an account, do the safety preflight. Then run what is safe to run.
  7. Generate the manual. expectation docs <dir> <out>, with results from a run if you have them.
  8. Audit it. Read the rendered pages without the author’s context, do the evidence pass, and update the coverage map.
  9. Report three verdicts, separately. See Reporting.

Auditing a suite

Writing the pages and auditing them are separate jobs, and an audit has three parts that answer different questions: is the product covered, can a reader follow the pages, and does the evidence back the claims. Record their findings separately: missing features, unclear steps, unsupported checks, simulated data, stale evidence and unsafe-to-run actions are different problems with different owners. A passing test does not approve the prose, and an approved specification does not prove the product works.

The zero-context read

“Read it as a newcomer” fails when the author does it, because the author fills the gaps without noticing. Give a fresh reader, ideally another agent or person without your context, one rendered tutorial on its own, with its screenshots, and no other page. They answer:

  1. Where do I start? Which screen, account and state; is anything assumed that the page does not set up?
  2. What do the numbers, units and symbols mean? SOL or dollars, per unit or total, a dot, a badge, a percentage of what.
  3. What changed? After each step, what is different on screen, and why it matters.
  4. What can I safely conclude? And what can I not conclude from this page.
  5. What do I do if it is empty, slow or fails? Is the non-happy path explained, or only tested?

Then they say whether the page teaches the user’s goal or just walks a test: a tutorial that toggles a currency back and forth five times passes and teaches nothing. Do the same for each feature page, with its linked terms. Fix what they could not answer in the descriptions, the Say:/Shows: and the stories, not in a note to the reviewer.

The evidence pass

A screenshot or a “passed” proves less than it seems to. It can come from a step that failed, show synthetic data, or mix fixtures with a live stream. For each claim on a page, say what supports it:

  • Observed: a run against the real system saw it, with results and screenshots saved.
  • Simulated: a run saw it, but against a fixture, mock provider, test account or fake data. Say which part was simulated.
  • Source-inspected: read in the code or docs, not run. Useful, not verified.
  • Unsupported: the driver cannot do the step yet. It shows as “not supported yet”, which is not “passing”.
  • None: an assumption. Say so, or ask.

Then check the evidence still matches the spec: results saved before the expectation, the Shows: or the UI changed are stale, and a screenshot from a failed or skipped step does not show the promised state. Expectation drops saved results itself when a test’s title or steps change: the test shows as “not run” until it runs again. It cannot tell that the UI or the wording around the steps changed, so that check is yours. A screenshot proves what is in it, at that step, with that data; it does not prove every claim on the page around it.

Safety preflight

Some journeys change the world: a trade, a payment, a follow, a notification, a new account. Before you run one, or offer someone a demo of one, answer:

  • What can it change? Every side effect of every step, including the ones the story does not mention (a confirmation email, a webhook, an on-chain transaction).
  • Where does it go? Which environment, account, network and provider receives it. Staging sign-in does not make the trade path go to staging.
  • What actually isolates it? A fixture, a sandbox, a testnet, a binding that refuses, or only a convention. Check the code path; do not assume from a variable name.

If you cannot show it is isolated, do not run it. Use a safe fixture, or leave the step unbound so it reports “not supported yet”. A gap that says so is better than a “pass” from a run that might have spent real money, and a demo must say plainly where its boundary is.

Evidence privacy

The evidence a run saves is a second kind of side effect. Screenshots, accessibility trees, view hierarchies, logs and HAR files can contain recovery phrases, private keys, passwords, tokens, and account data such as balances, addresses and names. Before you run, answer:

  • What is captured? Which steps take a screenshot or a tree, and what is on screen or in the request at that moment, including a secret shown by an earlier step that is still visible.
  • What keeps it out? A test account with nothing real in it, a redacting binding, a privacy screen the app shows when it is backgrounded or stopped, or a step that leaves the screenshot out. Check that it applies at the moment of capture; a privacy overlay that only appears on the next frame doesn’t.
  • Where does it go? The results directory, the generated manual, CI artifacts, a hosted site, a pull request. Anything committed or published is public to everyone who can see it.

If a step would capture a secret and nothing redacts it, don’t take that screenshot (or don’t run the step), and say in the report that the evidence was left out on purpose.

Reporting

Report three verdicts, because each can pass while another fails:

  1. The specification: is it complete and readable? The coverage map’s gaps and the zero-context read’s findings. expectation check and plan --coverage support this verdict but do not decide it: they check the model, not whether the manual teaches the product.
  2. The tests and observed behaviour: what ran, what passed, what failed, what is not supported yet, and how much of it was observed and how much simulated, and whether by an embedded or an external driver (see Remote drivers). An unsupported step did not run successfully, whatever the rest of the run did. Take this from the per-plan results, not the exit code: a run exits 0 when nothing failed, even if nothing was bound, and a missing screenshot is only a warning.
  3. Approval and product status: what is approved, what is proposed, what is Status: pending, and the open decisions with the question for each.

A tutorial can pass as a test and fail the documentation audit; it can read well and have no evidence. Say which. Also list the assumptions you made and the claims with no evidence, and do not present any of those as verified behaviour. Mark undecided behaviour Approval: proposed and ask.

Settled and proposed

Approval: approved and Approval: proposed mark what is agreed and what is not; see Approved-only manuals. A suite that does not use them is unchanged. Approval is about the specification; it is separate from Status: pending (the behaviour is not built yet) and from the test results.

Modelling an app with data

The vocabulary has two kinds of state: one of a few named values (locked | unlocked), and a number in a range (0..20 items). There are no strings, lists or records. That is what lets expectation check compare every expectation with every other one, and it is enough for products that are mostly data (invoices, tasks, users), once you know how to say them.

The rule: a state is something the user would notice changing, sorted into the cases the product treats differently. The exact data stays in the driver.

A list is a count

Don’t model each record. Model how many there are, and say changes relatively:

Vocabulary:
  State: the account has 0..50 invoices

Feature: Invoices
  Expectation: Creating an invoice adds a draft
    Given the viewer is not signed out
    And the account has below 50 invoices
    When the viewer creates an invoice
    Then the account goes up by 1
    And the invoice is a draft
  • Keep the range small. It only has to hold the cases that differ (none, one, some, full), not what the database allows. A wide range makes check print “search truncated”, which is harmless: the search stops at its depth limit.
  • A relative Then needs room. “Goes down by 1” from 0 is impossible, so say And the account has at least 1 invoice in the Given of anything that removes one, and below 50 in anything that adds one. A generated test keeps the Background’s value wherever the Given allows it, so a Given that allows the Background’s 0 gives a test that can’t pass.

The record in front of the user is a state

“The invoice” is the one the reader is looking at. Its life is a named state, and missing (or none) is a value like any other:

  State: the invoice is missing | a draft | sent | paid

Values can be more than one word. The driver decides which real record “the invoice” is: usually the one it created in arrange, or the newest.

When a journey really involves two records at once, name each by its role, not by a number: “the sender’s balance” and “the recipient’s balance”, not “account 1” and “account 2”.

Typed-in text is the case it falls in

A text field can hold anything, but the product only does a few different things with it. Model those:

  # What was typed, sorted by what the product does with it. The driver picks a real value
  # for each: "" for empty, "not-an-email" for malformed, "pat@example.com" for valid.
  State: the recipient's email is empty | malformed | valid

  Expectation: A draft with a valid recipient can be sent
    Given the invoice is a draft
    And the recipient's email is valid
    When the viewer sends the invoice
    Then the invoice is sent

  Expectation: A draft without a valid recipient stays a draft
    Given the invoice is a draft
    And the recipient's email is empty or malformed
    When the viewer sends the invoice
    Then the invoice is a draft

A story sets it like any state the outside world changes: When the recipient's email is valid. Say how the reader does that with a Set: line (Set: valid: type the customer's email address). The same works for a search with no | some | too many results, a password that is too short | accepted, or an upload that is too large.

Who is looking is a state

Roles and permissions are a state, and a rule for one role is an ordinary expectation whose Given names it:

  State: the viewer is signed out | a member | an admin

  Expectation: Only an admin deletes a sent invoice
    Given the viewer is an admin
    And the invoice is sent
    And the account has at least 1 invoice
    When the viewer deletes the invoice
    Then the invoice is missing
    And the account goes down by 1

  Expectation: A member cannot delete a sent invoice
    Given the viewer is a member
    And the invoice is sent
    When the viewer deletes the invoice
    Then the invoice is sent

The two Givens don’t overlap, so there is no conflict. If a rule is “anyone can, except…”, write the general expectation and make the exception Overrides: it.

Things you don’t control

A payment provider, a mail service or a price feed is a state of its health (live | delayed | unavailable) with an event for it failing. Feature docs that explain works one through.

What to leave out

  • Field-by-field content. That the invoice shows the right total is a unit test’s job. The suite says a total is shown, or that it is correct | stale if the product can show a stale one.
  • Every validation rule. One state with the cases that behave differently. Ten ways to be malformed are still malformed.
  • Internals. No “the cache is warm”, “the job is queued”, unless the user sees it.

If a part of the product needs none of this, such as a pure calculation, it doesn’t need to be in the suite.

What the driver does with it

The driver turns each case into real data, and that is the only place the data lives:

.arrange('the account', async n => { await db.reset(); await db.seedInvoices(n); })
.arrange('the invoice', async v => { if (v !== 'missing') current = await db.createInvoice({ status: statusOf(v) }); })
.arrange('the recipient\'s email', v => { email = { empty: '', malformed: 'not-an-email', valid: 'pat@example.com' }[v]; })
.observe('the account', () => db.countInvoices())
.observe('the invoice', async () => nameOf(await db.find(current?.id)))

arrange gets a value inside what the test’s start asks for: the first name allowed, or a number in the range. observe must give back exactly a declared value: a name as a string, a count as a number.

Several areas of one product

Billing, search and settings rarely share states. Give each its own directory under the suite: each top-level section is a system of its own, with its own Background, stories and flow graph. When two teams would otherwise pick the same words, Scopes: sections gives each section its own vocabulary (see The language).

How expectations are compared

A condition (a Given, a Then, a trigger) stands for a set of states: every combination of values that satisfies it. Everything below comes down to three questions about those sets:

  • do two overlap?
  • does one imply the other?
  • what’s left after an action overwrites some states?

Named values are bit sets and numbers are intervals, so the answers are exact. They are never guesses from sampling.

Outcome conflicts

Two expectations conflict when the same action can set off both, their Givens overlap, and their Thens contradict. In the overlap, the system can’t do both.

The error names the overlap (“both apply when the kettle is off and the child lock is on, and the dial is above 55 %”) and suggests which is the exception: the more specific one.

Invariant conflicts

An expectation with no When is an invariant: it holds whenever its Given does. It conflicts with an expectation that leaves the system where the invariant’s Given holds but its Then can’t, and with a Background that does the same.

Exceptions

An Overrides: between the two, directly or through a chain, settles a conflict. Where both apply, the overriding one’s Then wins.

  • Overrides must form a DAG. A cycle is an error (override-cycle).
  • An override between two expectations that never disagree gets a warning (unneeded-override).
  • Settled conflicts are listed in the docs as the suite’s exceptions, and the overridden expectation’s page links to each one: “Except when the child lock is on: see …”.

Relative Thens

Two different relative Thens (“goes up by 1” and “goes up by 2”) always disagree. A relative one and an absolute one disagree unless the shared situation pins down the one value where they meet.

The flow DAG

Starting from each section’s setup, and from each scenario’s arranged start, a breadth-first search applies every transition that can fire, and sees what state it leaves.

  • It only uses expectations from the same top-level section.
  • An expectation’s level is the fewest steps before it applies. Its parents are the expectations that take the last step on those shortest routes.
  • Levels only grow along edges, so the result is a DAG even though the behaviour loops (start, run dry, reset, start again).
  • Each expectation gets a shortest route from the start, which is a ready-made test for it. That’s what generated coverage tests follow.
  • An expectation the search never reaches gets an unreachable warning: nothing can test it.

The search has limits on depth and the number of states it visits. A counter that can keep going up (“the coin box goes up by 1”) makes new states forever, so the search stops at its limit and says “search truncated”. By then it has usually found every expectation.

expectation graph prints the DAG as Mermaid (or DOT with --dot), and the manual’s map page draws it, coloured by verdict.

Ways into a section

For each section, a goal-directed search finds the chain of expectations that gets from its parent’s setup to its own: “press PEN”, or “sign in, open a project, press PEN” for something deeper. That chain, without any step it works without, is the “Before you begin” of the section’s page.

If there is no such chain, it’s a no-way-in warning, because then nothing explains how to get there.

From stories to acceptance tests

A story describes a journey. It doesn’t have to say everything that happens along the way, because the expectations already do. Planning walks each scenario through the expectations, and turns it into a test plan: what to arrange, what to do at each step, and what to check after it.

What fires

An expectation fires at a step when the current state implies its Given, and the step’s action implies its trigger.

  • In a compound action (“When the dial is 0 % and the user presses reset”), the other changes happen first, then the event.
  • When an exception and the expectation it overrides both fire, only the exception’s Then applies.
  • After a step, the state is the old state with the Thens of what fired written over it.

What’s checked

Each step’s checks are:

  • the Thens of the expectations that fired,
  • the Thens of invariants now in force,
  • and the story’s own Thens.

The story never has to restate what the expectations promise. The tests check it anyway, so a story that only says “When the dial is 80 %” still checks that the kettle is heating.

What’s rejected

Planning is strict, because a story that relies on unspecified behaviour would test something nobody agreed on.

CodeWhen
unclear-steperrorThe step might set off an expectation, but the story doesn’t pin down whether. For example “the dial is at least 50 %” when an expectation needs “above 55 %”.
unspecifiederrorAn event happens and no expectation says what it does.
contradictserrorOne of the story’s Thens contradicts what the expectations say.
clasherrorTwo expectations fire and disagree, and nothing overrides.

Where a test starts

A test starts from its section’s setup (the Backgrounds, from the root down), with its scenario’s Givens written over it. The runner arranges that state before the first step, choosing a value inside each constraint: the first allowed name, or the middle of a range.

Coverage

An expectation that no story exercises gets an untested warning, with a route that would reach it:

warning[untested]: no story exercises «Running dry stops the kettle»
   = help: a story that would: When the dial is above 55 % / When the water runs out

Acceptance::with_coverage() (and expectation plan --coverage) adds a generated test for each one, following that route from the expectation’s own section setup. It also adds a test for each section that Follows: a setup the expectations get from, taking that route in and checking the section’s setup at the end. Generated tests are named “Reaching «…»”. They appear in the test report, but not as tutorials.

Acceptance::with_state_pictures() (and expectation plan --state-pictures) adds another kind, named “Visiting the state after «…»”: one for each state of the state map that is a move from a start and that no other test passes through. They add no verdicts. They are there so the state map has a screenshot of every state it shows at first. Each one arranges a start of its own, so on a system that is slow to set up they can be most of a run: leave them out of a quick run, and add them, after with_coverage(), when the run is for the manual.

fn main() {
let quick = Acceptance::load("expectations")?.with_coverage();
let for_the_manual = Acceptance::load("expectations")?.with_coverage().with_state_pictures();
}

Drivers

The runner talks to the system under test through a driver, in the vocabulary’s terms: set this state, make this event happen, what is that state now. You can implement the Driver trait, or build one from closures with Bindings.

Bindings

Bindings wraps your system (any value, called the world) and one closure per vocabulary term:

#![allow(unused)]
fn main() {
use expectation_harness::{Bindings, Progress, Screenshot};

let mut driver = Bindings::new(Kettle::default())
    .observe("the kettle", |k| k.phase_name())                  // read a state
    .observe("the dial", |k| k.dial)
    .set("the dial", |k, v| k.dial = v.as_f64().unwrap())       // change a state, as an action
    .arrange("the kettle", |k, v| k.force(v.as_str().unwrap()))  // put a state in place before a test
    .on("the user presses reset", Kettle::reset)                 // make an event happen
    .on("the water runs out", Kettle::run_out)
    .on_reset(|k| *k = Kettle::default())                        // before every test
    .on_settle(|k| k.run_for(1.0))                               // after each action
    .on_advance(|k| { k.run_for(0.1); Progress::Advanced })      // between looks
    .on_screenshot(|k| Screenshot::svg(k.svg()));                // after each step
}

Terms are matched the way steps are: ignoring case, extra spaces and a leading “the”.

MethodUsed for
observe(subject, f)Reading a state. Return a &str for a named value, or a number. Named values match the vocabulary ignoring case.
set(subject, f)A When that changes a state (“When the dial is 80 %”). Also used to arrange, unless there’s an arrange.
arrange(subject, f)Putting a state in place before the first step (the Background, a scenario’s Givens).
on(event, f)Making an event happen.
on_reset(f)Putting the system back to the start before each test.
on_settle(f)Letting the system settle after each action, before anything is observed.
on_advance(f)Letting a little time pass before the runner looks again.
on_screenshot(f)A picture of the system after each step: Screenshot::png, jpeg or svg.
on_exchanges(f)The HTTP requests the system made since the last call, with their responses: what an API’s manual shows instead of a screenshot. See APIs.
needs(&[…]), fresh(&[…])The external services the tests need.

The values passed to set and arrange are Values: v.as_str() for a named value, v.as_f64() for a number.

Time: settling and polling

Real systems take time to react. For each step the runner:

  1. acts: sets the states and makes the event happen;
  2. lets the system settle;
  3. observes every check. If they don’t all hold, it advances and observes again, up to RunOptions::patience times (100 by default). The step passes as soon as every check holds at once.

Polling is what lets “Then the kettle is heating” wait for the kettle to warm up. Settling is what makes “Then the kettle is off” mean that it stays off. Without it, the check could pass in the instant before the kettle switches on. Make the settle long enough for whatever should happen to happen, and for whatever shouldn’t to show.

A system with no time in it needs neither: the default advance returns Progress::Static, and the runner stops looking after the first observation.

Not supported yet

Before a test starts, the runner checks that the driver can do everything the plan needs: arrange each starting state, set each changed state, perform each event, observe each check. If it can’t, the test is not supported yet:

The driver can't arrange the child lock, arrange the dial, arrange the kettle and 6 more things yet.

That isn’t a failure. The system, or its driver, just doesn’t do it yet. The test’s steps get a placeholder instead of a screenshot, and the expectations only it would check are “not supported yet” in the docs. This lets a suite describe a whole product while its drivers catch up, and keeps the gap visible.

A driver that can arrange some values of a state and not others overrides Driver::can_arrange.

Controls: what exists, and what was used

A driver can list the buttons, fields, switches and links a person can act on, and say which ones its actions used. Then the report shows every control the tests found and which of them no test ever used, as interactions.md, site/interactions.html and interactions.json (for CI).

Bindings::new(World::default())
    .on_controls(|w| vec![Control::new("Settings", "export-log", "button", "Export log")])
    .on_used(|w| std::mem::take(&mut w.used)) // Control::key()s since the last call

Say which vocabulary event using a control makes happen with Control::mapped_to("the user presses lock"), and the report joins the control to the behaviour specified for that event and the stories about it. Each control then shows its gaps, with the reason: no event mapping, event not in the vocabulary, no expectation, only pending expectations, no authored story, never used by a test, no passing execution (in interactions.json: no-event-mapping, unknown-event, no-expectation, only-pending, no-authored-story, never-used, no-passing-execution). A story that performs the event in a section named like the control’s view documents the control even if it couldn’t run; it still isn’t verification. The same event on a control in another view is a different row, and what covers one doesn’t cover the other. An integration that knows controls no run will reach can list them with Acceptance::with_inventory.

Driver::controls is asked after a test’s start is arranged and after each step; the report keeps the union. Driver::take_used is emptied after arranging, so setting a test up doesn’t count, and read after each step. Give each control an id that doesn’t depend on its label, and the view it is in: the same id in two views is two controls. A story and a generated test are counted separately, and a control used only by tests that failed is not shown as working. The list is what the driver reported, not proof that nothing else is on screen. Turn it off with RunOptions { controls: false, .. } if listing is slow.

Attachments

A driver can hand over files it captured during each step, such as a network log, with Bindings::on_attachments or Driver::take_attachments. With RunOptions { attachments_dir: Some(dir), .. } the runner keeps them per run, test and step. Extensions use them to report which outcomes of a contract the tests saw. See Evidence and contract coverage.

HTTP exchanges

A driver for an API hands over the requests it sent and the responses it got, with Bindings::on_exchanges or Driver::take_exchanges. The runner redacts them and keeps them in the results, and the manual shows each step’s request as a curl command. See APIs.

The Driver trait

For full control, implement Driver yourself. Only set, perform and observe are required:

#![allow(unused)]
fn main() {
pub trait Driver {
    fn needs(&self) -> Vec<String> { vec![] }
    fn fresh(&self) -> Vec<String> { vec![] }
    fn reset(&mut self) -> Result<(), String> { Ok(()) }
    fn may_continue(&self) -> bool { true }
    fn arrange(&mut self, var: &Variable, value: &Value) -> Result<(), String> { self.set(var, value) }
    fn set(&mut self, var: &Variable, value: &Value) -> Result<(), String>;
    fn perform(&mut self, event: &Event) -> Result<(), String>;
    fn observe(&mut self, var: &Variable) -> Result<Value, String>;
    fn can_arrange(&self, var: &Variable, value: &Value) -> bool { true }
    fn settle(&mut self) {}
    fn advance(&mut self) -> Progress { Progress::Static }
    fn take_exchanges(&mut self) -> Vec<Exchange> { vec![] }
    fn screenshot(&mut self) -> Result<Option<Screenshot>, String> { Ok(None) }
    fn supports(&self, need: Need<'_>) -> bool { true }
}
}

Variable::key and Event’s key are the normalised names, for matching. Calls may block, so a driver can talk to a browser, a device or another thread. Any Err fails the step with that message.

Running

#![allow(unused)]
fn main() {
let acceptance = Acceptance::load("expectations")?.with_coverage();

// Run, and panic with every failure if anything failed:
acceptance.assert_passes(&mut driver, &RunOptions::default());

// Or keep the report:
let opts = RunOptions { docs_dir: Some("docs".into()), ..Default::default() };
let report = acceptance.run(&mut driver, &opts);
println!("{}", report.failures(&acceptance.suite, &acceptance.plans));
acceptance.docs(Some(&report)).write("docs")?;
}

With a docs_dir, screenshots go to <docs_dir>/screenshots/<test>/<step>.<ext>.

A test whose start can’t be set up (the reset or an arrangement fails) fails there, and its other steps are skipped. The runner still asks for a screenshot, so the report shows what the system looked like when it went wrong. If there is none, the failure stands as it is.

Starting where the last test ended

Resetting and arranging a start can be the slow part of a test. So when a test has passed, and everything the next one is given already holds, the runner starts the next one there: no reset, nothing arranged. It decides by looking. It observes each thing the test is given, once, and only continues if all of them hold as they are. It never continues from a test that failed, into a test that is given nothing, or across a Launch: that starts the program again.

To make the most of this, the runner picks the next test: one that starts where the last one ended if there is one, and otherwise the next in order. The report stays in the order of the tests. Each result says how the test began (PlanResult::began, a began line in the saved results), and the manual’s page for a test that continued says so. If a share looks wrong, that is where to look first.

The check only sees what the suite describes. Say no when a test leaves something behind that no state of the suite covers and that the next test could notice: a log, a clock, a cache, a counter.

fn may_continue(&self) -> bool { false }     // a Driver
Bindings::new(world).always_reset()          // Bindings
RunOptions { share_starts: false, ..Default::default() }   // one run

A driver that asks for services afresh before each test (fresh) never continues: those services must not keep what the last test left.

Saved starts

When several tests begin at the same arranged start and none of them ends where another starts, each one rebuilds it: a reset, then every Given. If building that start is slow (a simulator, a flight, a long sign-up) and the system’s state is something you can copy, the driver can save it:

// Bindings over a world that is plain data (it is Clone):
Bindings::new(world).checkpointed()

// Anything else: say how to save and put back.
Bindings::new(world).on_checkpoint(
    |w| Checkpoint::new(w.snapshot()),
    |w, cp| w.restore(cp.get::<Snapshot>().ok_or("not mine")?),
)

// Or on a Driver of your own:
fn checkpoint(&mut self) -> Result<Option<Checkpoint>, String>   // None: can't (the default)
fn restore(&mut self, checkpoint: &Checkpoint) -> Result<(), String>

The runner arranges the start once, and only when another test still to run begins there. It saves it after observing that everything the test is given holds. Each of the other tests with that start is put back to it, and then the runner looks at everything the test is given, as it does after arranging. If that doesn’t hold, or the restore fails, it resets and arranges as usual and forgets that checkpoint, so a bad restore costs time and never a wrong result. A saved start is dropped when no test left begins there, and a run keeps at most RunOptions::checkpoint_limit (8) at once.

A test that continued from the last one is still cheaper and is tried first. The result says how each test began: arranged, continued or restored, in the results, on the test’s page in the manual, and (restored) in expectation-run.

Save what a test could notice and the suite doesn’t describe, too: a clock, a log, a cache. If you can’t, or restoring is not exact, leave the default (no checkpoints), or turn sharing off for the run with share_starts: false or for the driver with always_reset() / may_continue, which turn checkpoints off along with continuing. A driver that asks for services afresh before each test (fresh) never restores.

A run as a gate

A run passes when nothing failed. Tests the driver can’t run yet, pending ones and ones that weren’t run don’t count against it, so a suite can be adopted a binding at a time. A release gate needs more: that the tests ran. Ask for it with a policy.

PolicyPasses whenexpectation-run
Policy::Lenientnothing failedthe default
Policy::Requiredevery test that isn’t pending ran and passed--strict
Policy::Allevery test ran and passed, with nothing pending--strict=all
 
#![allow(unused)]
fn main() {
acceptance.assert_passes_with(&mut driver, &opts, Policy::Required);

// Or with the report:
let report = acceptance.run(&mut driver, &opts);
if !report.meets(Policy::Required) {
    eprint!("{}", report.failures(&acceptance.suite, &acceptance.plans));
    eprint!("{}", report.incomplete(&acceptance.plans, Policy::Required));
}
}
  • report.incomplete lists each test that didn’t run with its status and why, and under Required the pending ones it let by, apart.
  • A run of no tests doesn’t meet Required or All: it verified nothing.
  • A policy judges the run that was just made. The report publish returns is merged with what earlier runs saved, and a pass saved earlier doesn’t stand in for a test that didn’t run now.
  • An expectation’s approval is about the spec, not the run. It plays no part.

Several runners

Acceptance::publish(dir, runner, &report) saves a run’s results as dir/results/<runner>.tsv, merges them with what other runners saved there, and writes the docs from the merged report. An API runner and a UI runner can each run their own part of one suite, and the manual shows both. expectation docs rebuilds the docs from saved results without running anything.

Results are keyed by each test’s name and a fingerprint of its plan, so results saved for an older version of a test are ignored, not misapplied. Each result also records the id of the run it came from and when each step ran, so evidence gathered outside the run can be matched to it (see Evidence and contract coverage).

Running in parallel

run_parallel runs the tests on n worker threads. Each worker builds its own driver (and its own services) by calling your closure with the worker’s number, so nothing is shared: give each one its own app instance, port, database or screen.

let report = acceptance.run_parallel(4, &RunOptions::default(), |n| {
    Worker::new(MyDriver::start(8000 + n as u16))
        .with_services(services_for(n))
});

Workers take a test as they finish one (one that starts where their last one ended, if there is one), and the report is in the order of the tests. The closure runs on the worker’s thread, so a driver need not be Send.

Remote drivers

Some systems can’t be driven from inside a Rust test: a phone app in a simulator, a desktop app in its own process, a React Native bundle. For those, the runner talks over a small protocol to a client that binds the vocabulary. That client lives in one of two places:

  • Embedded in the app. It calls the app’s own actions and reads its state directly.
  • In a test process outside the app. An adapter in a WebdriverIO, Appium, XCUITest, Espresso or Playwright run drives the app through its UI and reads what the UI exposes.

In the app

Each client binds the vocabulary the same way Bindings does in Rust: one closure per term.

Swift (iOS, macOS, SwiftUI, UIKit)

// A local package: clients/swift in the repository (see its README for adding it)
import ExpectationDriver

let driver = ExpectationDriver(platform: "SwiftUI", app: "Kettle")
    .observe("the kettle") { .name(kettle.phase.name) }
    .observe("the dial") { .number(kettle.dial) }
    .set("the dial") { kettle.dial = $0.number ?? 0 }
    .arrange("the kettle") { kettle.force($0.string ?? "off") }
    .on("the user presses lock") { kettle.pressLock() }
    .onReset { kettle.restore() }
driver.start()   // connects only when EXPECTATION_URL is set

Handlers run on the main actor. On UIKit platforms, screenshots of the key window are taken for you. The app needs NSAllowsLocalNetworking under NSAppTransportSecurity in its Info.plist to reach the runner over plain HTTP. In the simulator, pass the runner’s address with SIMCTL_CHILD_EXPECTATION_URL=http://127.0.0.1:4477 xcrun simctl launch ….

JavaScript (React Native, web, Node)

// clients/js in the repository (expectation-driver; not on npm yet, see its README)
import { ExpectationDriver } from 'expectation-driver';

Handlers may be async. There’s no built-in screenshot in JavaScript: pass onScreenshot (returning a base64 PNG), or let the runner take them from outside.

Rust (GPUI, egui, Bevy, anything with a main loop)

#![allow(unused)]
fn main() {
use expectation_remote::client::{Client, Handlers};

let handlers = Handlers::new()
    .observe("the kettle", |v: &KettleView| v.kettle.phase_name())
    .set("the dial", |v, x| v.kettle.dial = x.as_f64().unwrap_or(0.0))
    .on("the user presses lock", |v| v.kettle.press_lock());
let client = Client::connect_env(handlers.hello("GPUI", "Kettle"));

// On the UI thread, every frame or tick:
while let Some(request) = client.try_recv() {
    handlers.handle(&mut view, request);
}
}

The client runs on its own thread; try_recv hands each command to the thread that owns the app.

Outside the app

The JavaScript and Rust clients don’t have to run in the app. In a UI-automation run they run in the test process, and each handler drives the app through the automation API. (Any test framework that can make HTTP requests can do the same; see the protocol.) With WebdriverIO, for example:

import { ExpectationDriver } from 'expectation-driver';

const driver = new ExpectationDriver({ platform: 'iOS', app: 'Kettle' })
  .observe('the kettle', async () => (await $('~kettle-status')).getText())
  .on('the user presses lock', async () => (await $('~lock')).click())
  .onScreenshot(() => browser.takeScreenshot());
driver.start(process.env.EXPECTATION_URL);

Bind only what the UI really shows and lets a person do. Anything else stays unbound and is reported as “not supported yet”, which is honest: a binding that reaches round the UI into the app’s internals is an embedded driver in disguise, and should be reported as one.

In the runner

Wherever the client lives, the runner’s side is the same: a RemoteDriver that listens for it and runs the suite through it.

#![allow(unused)]
fn main() {
use expectation_remote::RemoteDriver;

let mut driver = RemoteDriver::listen("127.0.0.1:4477")?
    .settle_for(Duration::from_millis(1000))
    .screenshot_with(|| simulator_screenshot());   // optional: from outside the app
let app = driver.wait_for_app(Duration::from_secs(60))?;
let acceptance = Acceptance::load_for("expectations", &app.platform)?.with_coverage();
let report = acceptance.run(&mut driver, &RunOptions::default());
}

RemoteDriver knows what the client can do from its hello, so anything it didn’t bind is “not supported yet”, not a failure. Time is real: it sleeps to settle after each action and between looks. If no app connects, every test is “not supported yet”.

So report.passed() means only that nothing failed. A run where nothing was bound passes. Check what you expect: that the stories meant to pass did pass (report.count(Status::Passed) and each result’s status), and that the screenshots you need were taken (driver.screenshot_error()).

Each command the runner sends gets 10 seconds to be answered. For apps whose actions take longer, .command_timeout(Duration::from_secs(240))? raises that deadline (it must be positive; there is no unlimited mode). It is separate from wait_for_app, which only covers the first hello, and from the settle and poll intervals. A timeout fails the command, naming it and the deadline, but it doesn’t cancel the work in the app: let it finish, or stop it safely, before the next action or before ending the session.

Or skip writing a runner and use expectation-run:

cargo install --git https://github.com/ptescher/expectation expectation_remote
expectation-run expectations --platform SwiftUI --docs docs --runner app

--stylesheet CSS and --state-shot-ratio W:H style the generated docs as they do for expectation docs (see the manual); bad values fail before the run. --command-timeout SECONDS sets that per-command deadline (--wait only covers connecting). --no-state-pictures leaves out the tests that only visit a state for the state map’s picture of it: a quicker run with the same verdicts (see Stories). A test starts where the last one ended when what it is given already holds there, and is printed with (continued); --no-shared-starts resets before every test (see Drivers). The remote protocol has no command for saving a start yet, so a remote driver arranges every start that isn’t continued. It listens, waits for the app, runs the suite for that platform, prints the results, and with --docs saves them and writes the manual. --screenshot-cmd 'xcrun simctl io booted screenshot "$1"' takes screenshots from outside, for apps that don’t take their own. --screenshot-store DIR keeps screenshots by content in DIR and builds the docs from there (see Screenshots in large projects).

It exits 1 if a test failed and 0 otherwise, including when every test was “not supported yet”, unless the run is --strict (see A run as a gate). A failed screenshot is only a warning on stderr. Read the per-plan lines it prints (✓ passed, ✗ failed, – anything else) or the plan rows in docs/results/<runner>@<platform>.tsv, and check the ones you expect to pass, before calling anything verified.

The protocol

JSON over HTTP/1.1. Anything that can make an HTTP request can be a client.

RequestBodyAnswer
POST /hello{"platform", "app", "observe": [..], "set": [..], "arrange": [..], "events": [..], "screenshot": bool, "reset": bool, "controls": bool, "attachments": bool}{"session": n}
GET /next?session=na command (200), nothing yet (204: ask again), or 410: say hello again
POST /reply?session=n{"id", "value"}, {"id", "png"}, {"id", "svg"}, {"id"} or {"id", "error"}204

A command is one of:

{"id": 1, "op": "reset"}
{"id": 2, "op": "arrange", "subject": "the kettle", "value": "off"}
{"id": 3, "op": "set", "subject": "the dial", "value": 80}
{"id": 4, "op": "perform", "event": "the user presses lock"}
{"id": 5, "op": "observe", "subject": "the kettle"}
{"id": 6, "op": "screenshot"}
{"id": 7, "op": "controls"}
{"id": 8, "op": "used"}
{"id": 9, "op": "attachments"}

Terms are the app’s own spelling from its hello. A named value is a JSON string and a number is a JSON number. png is base64.

An app that says "controls": true can list what a person can act on, and the report then shows which controls no test used (see Controls). controls answers with controls, a list of {"view", "id", "kind", "label", "event"} (the last three optional; event is the vocabulary event using the control makes happen). used answers with used, a list of {"view", "id"} for the controls set and perform acted on since the last used, and empties it. In Rust that is Handlers::on_controls and on_used, in JavaScript onControls and onUsed, in Swift controls and used.

An app that says "attachments": true can hand over files it captured, such as a network log. After a test’s start and after each step, the runner sends attachments. The app answers with attachments, a list of {"name", "type", "text"} or {"name", "type", "base64"} for what it captured since it was last asked, and empties it. expectation-run --attachments DIR keeps them. In Rust that is Handlers::on_attachments, in JavaScript onAttachments. The Swift client doesn’t offer it yet, but any client can answer the command. An error from the handler, or a capture that is neither text nor base64, means no captures for that step; the test goes on. See Evidence and contract coverage.

Events: real taps or the app’s actions?

An embedded client makes an event happen by calling the same action the button calls, not by synthesising a tap. That’s fast, works the same on every stack, and tests the behaviour. It doesn’t test that the button is wired to the action, or that it’s visible. If that matters, pair the suite with a UI-automation smoke test (XCUITest, Espresso, Detox), bind the event to a handler that drives the UI, or run the suite through an external adapter.

External services

Tests sometimes need something that isn’t part of the system under test: a database, a server, a container. The harness treats that as a service, so no test, driver or script has to start it.

#![allow(unused)]
fn main() {
use expectation_harness::service::{Command, Docker, Ready, Services};

let mut services = Services::new()
    .with(Command::new("server", "./target/debug/server").ready(Ready::Tcp(8080)))
    .with(Docker::new("database", "postgres:16").port(5432, 55432)   // a database is a container
        .env("POSTGRES_PASSWORD", "test").ready(Ready::Tcp(55432)));

let mut driver = Bindings::new(world).needs(&["server", "database"]).fresh(&["database"]);
let report = acceptance.run_with(&mut driver, &RunOptions::default(), &mut services);
}

Needs

A driver says what it needs (Driver::needs, or Bindings::needs). Before each test, the runner makes sure each one is up: one that is up stays up, and one that died is started again. They all stop when services is dropped, the last started first.

A test the driver can’t run anyway starts nothing.

Fresh

What a test leaves behind (rows the last test wrote, a user it signed in) is cleared by naming the service in Driver::fresh. It’s started afresh before each test that runs.

Not supported yet, not failed

A service that can’t run on this machine (no Docker, no build) makes the tests that need it “not supported yet”, and the reason says how to get it:

database: install PostgreSQL with `brew install postgresql`

A test suite on a laptop without Docker still runs everything else, and the gap is visible in the docs.

Providers

ProviderStarts
Command::new(name, program)A program, with .arg, .env and .hint (how to install it). Ready when .ready(…) says so.
Docker::new(name, image)A container, with .port(inside, outside), .env, .container(name). .build_from(dir) builds the image when it isn’t there. On a Mac, it wakes Docker Desktop.
Present::new(name, path)Nothing: a build or a file that must exist.
Fallback::new(name, ways)The first of several ways that’s available: a native build, else a container.

Ready::Tcp(port) waits until the port answers. A port that something else already holds is an error, not a ready service: whatever answers there is probably left over from an earlier run.

Anything else implements the Service trait: a name, whether it can run here (unavailable), and start, which returns a Running that stops when it’s dropped.

The generated manual

Docs::write produces a manual, both as an HTML site in site/ and as Markdown that GitHub renders. It reads like a project’s user documentation, not a test report. The test evidence is all there, folded away.

#![allow(unused)]
fn main() {
acceptance.docs(Some(&report)).write("docs")?;
}

or, from results that runs have saved in docs/results/:

expectation docs expectations docs

expectation docs checks the links in the HTML it wrote and warns about any that go to a file or an anchor that isn’t there.

A test whose wording has changed since its results were saved is shown as not run, not as unsupported (another runner that can’t do it says nothing about whether this one did). If its steps are still the same, each keeps its last screenshot, captioned “From before this page changed”, so a published manual keeps its pictures between full runs.

Navigation and size

Each page lists only the sections on the way to it, with the others as links. Opening one fills in what is under it from site/assets/nav.js, which is written once for the whole site, so a page’s size does not grow with the manual. A section with more than 30 subsections shows them under one “N more sections” entry. It works from disk and from any static host; without scripts the sidebar shows the current section and links to the rest.

With more than 300 tests, the test report (site/tests.html) is an index: one row per section, with its results, linking to that section’s own report (site/tests-<section>.html), which lists its tests and what isn’t verified yet. With more than 300 expectations, the map (site/map.html) is likewise a list of sections, each drawn on its own page (site/map-<section>.html). Smaller manuals keep one page each. The Markdown report is always one file.

Approved-only manuals

Mark what is agreed with Approval: approved and what is not with Approval: proposed (see the language), then write a manual of just the agreed part:

expectation docs expectations docs-approved --approved-only --results docs/results

The full suite is still checked first and must be clean. Then only what is approved is kept, before the suite is read, so the manual is one where the rest was never written:

  • A feature stays if any of its expectations is approved (its own, or its feature’s). Its description stays only if the feature itself is approved. A feature with nothing approved is gone, with its page, navigation entry and every link to it; a [[link]] to something left out reads as plain text.
  • A story is a tutorial only if it is approved itself. Its test page goes with it.
  • The vocabulary, terms and backgrounds stay. They aren’t behaviour.
  • An approved story or expectation that depends on one that isn’t (a story steps through a proposed expectation, or an approved expectation overrides one) is an error that names the problem, so the approved manual can’t present proposed behaviour as agreed. Approve the other one, or leave this out.
  • Nothing marked approved means an empty manual, with a warning.

--results says where the saved results are, since the output directory is usually not the one the full manual and its results/ live in. Test results are what runs saw and are shown as they are: an approved specification may still fail, or not be testable yet. Without the flag, nothing changes, and neither do checking, planning or running.

Your own theme

The site loads a CSS file of yours after its built-in styles, so a team can give the reports its documentation’s look without forking or editing generated files:

expectation docs expectations docs --stylesheet brand.css

#![allow(unused)]
fn main() {
let acceptance = Acceptance::load("expectations")?.with_stylesheet("brand.css")?;
}

expectation-run takes --stylesheet too. The file is copied to site/assets/custom.css and linked from every page of every platform’s manual: tutorials, test results, interaction coverage, both maps and the theme page. Put a file called theme.css in the suite’s directory and it is used without the flag, so regenerating, or restyling from saved results without running a test, keeps the theme. Results, screenshots, links and pass/fail never depend on it. A stylesheet that is missing, empty or has unbalanced braces is an error, not a fallback. Without one, the site is exactly the built-in Day and Night.

Override the colour, type and shape tokens (--canvas, --ok, --font-sans, --radius-panel, …; the generated theme page lists them all) or any component’s CSS by selector. The built-in dark rule is more specific than :root, so set a token for Day (:root), for dark readers (@media (prefers-color-scheme: dark) { :root:not([data-theme="day"]) { … } }) and for :root[data-theme="night"]. The file is copied as written: a relative url() in it resolves beside site/assets/custom.css, so use data: URLs to stay self-contained and usable offline. For accessibility keep text at 4.5:1 against its surface in each mode, and keep result states distinguishable without colour: the words verified, failed and not supported yet stay on the page.

The state map’s cards draw each screenshot at the shape you give with --state-shot-ratio (with_shot_ratio in Rust), for example 9:19.5 for phone screens.

See the kettle manual for a whole one.

Pages

  • Tutorials, one per story scenario: the story’s introduction, Before you begin (the setup, in the specs’ own words), then numbered steps. Each step says what to do (from the Say:s and Set:s), what you’ll see (the story’s Thens, or what the expectations promise) and shows the screenshot the test took there.
  • Topic pages, one per feature: its description, then each expectation as a sentence (“If the kettle is off, press START. The light comes on and the water starts to heat.”), its exceptions as notes, a screenshot of it in action, and the tutorials that show it.
  • Section pages: the description, Before you begin (the setup, or the steps that get there from the parent section), the topics in it, and its tutorials as cards.
  • Reference: the glossary of Term:s, the map of the flow DAG, the theme, and the test report: every test and its result, and a page per test with each step, check and screenshot.
  • Test vocabulary: each state, event and phrase, and how the docs word it.

On every page, the test details of each expectation (its Gherkin, what it follows and leads to, its verdict and the tests that cover it) are collapsed under “How this is tested”. Generated coverage tests appear only in the test report. A step without a screenshot shows a “Not supported yet” or “No screenshot” placeholder.

Previews of some sections

A pull request that touches one area needs a preview of that area, not the whole manual:

expectation docs expectations preview --section Billing --section 04-orders/returns \
  --base-url https://docs.example.com/manual/

--section takes a section’s name (ignoring case), its slug, or its directory. Give it more than once for several sections. A name that two sections share is an error that lists their directories.

What the preview has:

  • the pages of those sections and everything under them: their features, tests and tutorials, and their own test report and map pages when the manual is split by section;
  • the Markdown overview (README.md) and the site’s assets.

What it leaves out: the pages about the whole suite (the test report, the maps, the glossary, the vocabulary, the interactions and contracts).

Links. The navigation still shows the whole tree. A link to a page the preview doesn’t have goes to the same page under --base-url: the address of the full manual, the directory expectation docs wrote it to. Without --base-url, such a link reads as plain text. Either way no link is broken.

What doesn’t change:

  • The whole suite is still loaded, checked and planned, and the results are the whole suite’s. A preview of one section is not a way past an error in another.
  • Writing a preview into a directory that holds a full manual removes nothing from it.

Screenshots in large projects

By default a run writes each step’s screenshot to screenshots/<test>/<step>.png in the docs directory, replacing the last run’s. That is simple, but every run rewrites every image. At 2,000 tests of five steps that is around a gigabyte per platform, and none of it diffs.

Keep them by content instead. Give the run a store:

  • RunOptions { screenshot_store: Some(dir), .. };
  • expectation-run --screenshot-store DIR.

Each screenshot is then named by its SHA-256 (DIR/<hash>.png) and written only if no screenshot with the same content is there yet. Identical frames across steps and runs are stored once, and an unchanged test writes no new file. The results name it screenshots/<hash>.png, the same kind of path as before, so older readers still work. Re-run unchanged tests and the results file is the same, apart from its run and window lines, which say which run it was and when each step ran (see Evidence and contract coverage).

Tell the docs where the store is with expectation docs --screenshots <dir|url> (or Acceptance::with_screenshots; expectation-run --screenshot-store does both):

  • A directory. The screenshots the pages show are copied into the docs’ screenshots/.
  • A URL prefix, for a store you sync to a bucket or keep as a CI artifact. The pages link to <prefix>/<hash>.png and nothing is copied: https://cdn.example.com/shots makes screenshots/abc….png into https://cdn.example.com/shots/abc….png. Images load lazily.

A store can also be the docs’ own screenshots/ directory; then there is nothing to copy.

Thumbnails. The state map’s cards and the story cards show thumbnails when a tool can make them: ImageMagick (magick, or mogrify from version 6), or sips on macOS. Each is made once, as screenshots/thumbs/<name>, and again only when its screenshot changes. Without a tool, or with EXPECTATION_THUMBNAILS=off, the cards show the screenshots themselves. SVG screenshots need none, since the browser draws them at any size. With a URL prefix there are no thumbnails.

Prune what no run names any more:

expectation screenshots prune DIR docs/results [more/results ...] [--dry-run]

It reads every results file in the directories given, every platform’s, and removes the files in the store (and its thumbs/) that none of them names. It only touches files named by a hash, and with no results files at all it removes nothing.

Where the store lives is your choice. Commit the specs and results/*.tsv in any case, and leave out the generated pages and thumbnails (add screenshots/thumbs/ to your .gitignore, as this repository does).

  • In Git. Make the store a directory in the repository, the docs’ own screenshots/ say, and commit it. Because names are content, an unchanged screenshot is never a new commit, and only changed frames add to the history. Run screenshots prune before committing to drop the ones no test takes any more. This is the simplest, and enough for most projects.

  • In Git LFS, when the images are large or many. Run expectation screenshots lfs <store> once. It writes <store>/.gitattributes so that PNG, JPEG and WebP files go to LFS; SVGs stay in Git, as text. Then commit as above. Git LFS must be installed (git lfs install). A clone fetches only the versions it checks out.

  • In a bucket, when it shouldn’t be in the repository at all:

    expectation screenshots push DIR s3://bucket/shots   # after a run
expectation screenshots pull s3://bucket/shots DIR   # before building docs elsewhere

    These run the provider’s own tool, with its own credentials and configuration:

    • s3://… uses the AWS CLI. S3-compatible stores such as R2 or MinIO work with AWS_ENDPOINT_URL set.
    • gs://… uses gcloud storage, or gsutil without it.
    • name:path is an rclone remote, which covers most others.

    Both directions add what the other side lacks and delete nothing; --dry-run shows what they would copy. To build the docs, either pull the store first and pass --screenshots DIR, with thumbnails, or pass the bucket’s public or CDN address, --screenshots https://…, so the pages link there.

None of these is required. Without a store, screenshots stay where they always were.

Keep hashes stable. A screenshot only matches the last run’s if every pixel does:

  • hide or freeze clocks and anything else that shows the time;
  • turn off animations and the blinking caret;
  • use the same fonts, data, device and scale each run.

A screenshot that changes on every run is stored again on every run.

The reader edition

The manual is read by people who want to learn the product, not test it. The default edition keeps every gap in view for the authors; for readers, build the reader edition:

expectation docs expectations docs --reader

(Edition: reader in outline.txt, --reader on expectation-run, or Acceptance::with_reader do the same.) Tutorials and topic pages then have no “How this is tested” block, no “Tested by” list and no “Its report” link, and a step with no screenshot shows just the step and what you see, with no placeholder or caption. The test report, the map, the state map and the vocabulary are still written, linked from one “For developers” entry in the sidebar. Nothing about the tests or their results changes.

The outline

By default the manual follows the sections. A suite can have an outline.txt beside its sections to shape it like a book:

Part: Start here
  Page: installing          manual/installing.md
  Page: the-installer [desktop]
Part: Brewing
  Section: The kettle

  • Parts group the top-level sections. They’re the navigation’s labels and the README’s contents.

  • The order is the order the reader meets them in, and so the previous and next links.

  • Pages are hand-written Markdown files in manual/ (install, reference, troubleshooting), placed among the generated ones. A page’s title is its first # line. They can use [[links]] into the generated pages. [desktop] keeps a page out of another platform’s manual.

  • Next: tutorials (a line of its own) makes Next and Previous follow the pages, the section pages and the tutorials only. The topic pages stay in the sidebar and in each tutorial’s “Learn more”, so a beginner pressing Next goes from tutorial to tutorial. With an outline, the glossary is the last page of the chain.

  • A section page lists its own tutorials first, then those of its subsections, even where the outline reads a subsection earlier than the section that holds it.

The sections themselves stay where they are, because their setups inherit from their parents. A top-level section that no part names goes into a last part, “More”, with a warning.

The look

The site is static HTML and CSS with a little JavaScript: assets/nav.js fills in the sidebar (see Navigation and size), and the states map (states.html) draws itself from data in the page. Neither is needed to read it: without scripts every page reads and links, the sidebar shows the current section, and the states map falls back to a list of the start states and where they lead. It follows the reader’s light or dark preference. The colours, type and corners come from the expectation_theme crate, and the theme page in each manual shows them.

APIs: requests as evidence

A suite can describe a system that has no screen: an HTTP API. The vocabulary, the expectations, the stories and the checks work as they do for an app. Only the evidence is different. Where an app’s manual shows a screenshot of each step, an API’s manual shows the request the step sent, as a curl command, and the response it got.

curl -X POST "$BASE_URL/v1/invoices/in_0002/void" \
  -H "Authorization: Bearer $MEMBER_API_KEY"

HTTP/1.1 403 Forbidden
Content-Type: application/json

{
  "error": {
    "type": "forbidden",
    "message": "Only an admin of the account can void an invoice."
  }
}

Every example in the manual is a request a test made against the API, so it can’t drift away from what the API really does. crates/harness/examples/invoices runs the whole thing against a stand-in invoices API:

cargo run -p expectation_harness --example invoices                  # docs in target/expectation-docs/invoices
cargo run -p expectation_harness --example invoices -- out --bug     # members can void: a failure

Writing the suite

Write it about what callers do and what the API promises, as you would for an app. The events are what a caller asks for (“the caller voids the invoice”), and the states are what a caller can read back (“the invoice is open”). Who is calling is a state too, so the rules that depend on it can be written as exceptions:

Vocabulary:
  State: the invoice is none | draft | open | void
    Shows: void: the invoice's `status` is `void`
  State: the caller is admin | member
    Set: use the {value}'s API key
  Event: the caller voids the invoice
    Say: void the invoice

Feature: Voiding
  Expectation: Voiding an open invoice voids it
    Given the invoice is open
    When the caller voids the invoice
    Then the invoice is void

  Expectation: Members can't void
    Overrides: Voiding an open invoice voids it
    Given the invoice is open
    And the caller is member
    When the caller voids the invoice
    Then the invoice is open

expectation check finds the permission rule that conflicts with the rule it is an exception to, as it would for any two expectations that promise different things in the same situation.

The driver

The driver calls the API with whatever HTTP client you use, and keeps each request it sends with the response it got as an Exchange. The runner takes them with on_exchanges (or Driver::take_exchanges):

use expectation_harness::{Bindings, Exchange};

let x = Exchange::new("POST", format!("{base}/v1/invoices/{id}/void"))
    .header("Authorization", format!("Bearer {key}"))
    .response(403)
    .response_header("Content-Type", "application/json")
    .response_body(body);

Bindings::new(World::new())
    .observe("the invoice", World::status)        // GET /v1/invoices/{id}
    .on("the caller voids the invoice", World::void)
    .on_exchanges(|w| std::mem::take(&mut w.log))

Hand them over as they were sent, credentials and all: the runner redacts them (below). It asks after arranging a test’s start, after each action and after each step’s checks, so it knows what each request was for:

RoleWhenWhere the manual shows it
setupwhile the test’s start was arrangedon the test’s page, folded away
actionwhile the step’s action ranon the tutorial, the feature page and the test’s page
checkwhile the step’s Thens were read backon the test’s page, folded away

The same request sent again in a row, such as a check that polled until it held, is shown once, with how many times it was sent.

What is kept

Exchanges are kept in the results file (results/api.tsv), which is published with the manual. So the runner keeps only what RunOptions::redaction lets through:

  • Only a few headers: Accept, Content-Type, Idempotency-Key, If-Match, If-None-Match and Prefer on requests, and Content-Type, ETag, Location and Retry-After on responses. Cookies and anything a gateway added are dropped.
  • Authorization keeps its scheme, and the key becomes $API_KEY, or the name you give it in keys. So does the value of an X-Api-Key or Api-Key header.
  • Query parameters, form fields and JSON fields named like a secret (password, token, client_secret, api_key, cvc and the like), and those you list in fields, read REDACTED.
  • A loopback address (http://127.0.0.1:53211) becomes $BASE_URL. Set base_url to show another origin instead, such as https://api.example.com.
  • JSON bodies are pretty-printed, with numbers kept as they were written. A JSON body that doesn’t parse can’t be checked for secrets, so it is replaced with a note. A body over max_body (16 KiB) is cut short.
RunOptions {
    redaction: Redaction {
        keys: vec![
            (ADMIN_KEY.into(), "$ADMIN_API_KEY".into()),
            (MEMBER_KEY.into(), "$MEMBER_API_KEY".into()),
        ],
        fields: vec!["email".into()],
        ..Default::default()
    },
    ..Default::default()
}

Name the keys when who is calling matters, so the reader can tell an admin’s request from a member’s. A name is a $ followed by capitals, digits and _. The curl commands leave those for the shell to fill in, and escape any other $.

Redaction is by name and by header, so it can’t know that a field called note holds a customer’s address. Read what the manual shows before you publish it, and add such fields to fields.

Limits

  • Bodies are text. Hand over a binary body as a note of what it was.
  • The remote drivers (Swift, JavaScript, the embedded Rust client) don’t send exchanges yet.
  • A step with both a screenshot and requests shows both: an app that calls an API can show its screen and its requests.
  • Exchanges are for the manual. To hold the traffic against an OpenAPI document, capture it as HAR too and use the HAR and OpenAPI extension.

Evidence and contract coverage

A story can pass while only ever exercising an API’s happy path. Contract coverage shows what the tests’ runs actually did against a contract, such as an API’s documented responses, an event catalogue or a list of error codes. It shows what was seen, what was not, and what nobody can tell, with each observation linked to the test step that made it.

Expectation doesn’t read network captures or API specifications. It records what an extension needs to line evidence up with the tests: the run’s id, when each step ran, and any files the driver captured. It also reads back what the extension made of that evidence. The extension does the rest: it parses a HAR, matches requests to an OpenAPI document, and decides which responses and values were seen. Any language will do.

Contract coverage finds candidates for a person to review. It doesn’t pass or fail anything, and it changes no test’s result or expectation’s verdict. If a documented outcome was never observed, it may deserve a story, but whether it does is a product decision.

What a run records

Every run has an id, and every step that runs has a window: wall-clock milliseconds since the Unix epoch, from the start of its action (or, for the test’s start, from resetting it) to after its screenshot. Both are saved in the results file, as lines that older readers skip:

expectation-results 1
run         <run id>  <started ms>
provenance  <part>  <value>
plan        <slug>  <status>  <fingerprint>
step        <n>  <status>  <polls>  <screenshot>  <error>
window      <n>  <start ms>  <end ms>
attachment  <n>  <media type>  <path>
check       ...

A run line applies to the plans after it. Step 0 is the test’s start; 1 is its first step. Results saved before runs had ids still load. Their tests have no run, so no evidence can count for them.

What a run was against

A test’s fingerprint says the test hasn’t changed. It says nothing about the program: a pass saved for one build still stands when the manual is written for the next. So a run can say what it was against, and the results keep it:

#![allow(unused)]
fn main() {
let opts = RunOptions {
    provenance: Provenance {
        app_revision: Some("3f2a9c1".into()),   // a commit, a version, a build number
        data_mode: Some("fixtures".into()),     // fixtures, live, recorded
        fixture: Some("seed-7".into()),         // which one, by a name
    },
    ..Default::default()
};
}
expectation-run expectations --docs docs --app-revision 3f2a9c1 --data-mode fixtures --fixture seed-7
  • Each part is optional. A part nobody gave is unknown, and is never guessed.
  • Nothing is read from the environment. The results and the manual publish what you give, so give a name, not a credential or the data itself.
  • The results file has a provenance line for each part, after the run’s line. Older files have none, and still load.
  • A manual merged from several runs keeps each result’s own run, so two tests on one page can be about two builds. Each test’s page says what its result was run against.

Say what the manual is for, and each test’s page says whether its result is about that:

expectation docs expectations docs --expect-app-revision 4b7d210
The runThe page says
said the sameit is what this manual is for
said something elseit is what another run saw, and not a failure of this build
didn’t sayit isn’t known

The test report’s first page counts the three. A result is never changed, hidden or failed because of what it was run against: the verdict is still the run’s. expectation-run --docs writes the manual for what it was run against, and Acceptance::with_expected does the same from Rust.

Attachments: what the driver captured

A driver can hand over files after the test’s start and after every step, such as the network requests that step made or a log. The runner saves each one as it is, under the step it was taken after, and records where in the results:

Bindings::new(World::default())
    .on_attachments(|w| vec![Capture {
        name: "network.har".into(),
        media_type: "application/har+json".into(),
        bytes: w.take_har(),
    }])
RunOptions { attachments_dir: Some("captures".into()), ..Default::default() }

Files go to <attachments_dir>/<run>/<test>/<step>/<name>. Names are reduced to letters, digits, ., _ and -, and can’t leave the directory. Without attachments_dir the runner still asks for them, so the driver’s buffer is emptied every step, but keeps nothing.

An app with an embedded driver says "attachments": true in its hello and answers the attachments command (see Embedded drivers). In Rust that is Handlers::on_attachments. With expectation-run, pass --attachments DIR.

Keep attachments out of the docs directory. A capture can hold authorization headers, cookies, request bodies and personal data, and a docs directory is made to be published. The runner never copies attachments into the manual, and nothing in a coverage file has room for them. Keeping secrets out of a capture in the first place is the driver’s job.

Attachments are optional. An extension can also read a capture made by any other tool (a browser’s HAR export, Playwright, a proxy) and match its entries to steps by time.

The HAR and OpenAPI extension

extensions/har-openapi holds captured HTTP traffic against an OpenAPI 3.0 or 3.1 document:

expectation-run expectations --docs docs --attachments captures
npx expectation-har-openapi --results docs/results/app.tsv --attachments captures \
  --openapi api.yaml --source live --complete
expectation docs expectations docs

Each documented status (exact, range or default), each enum value and each oneOf/anyOf branch of a JSON response becomes an outcome. It also reads a HAR made by any other tool (--har), and places its requests in steps by time. Its README lists what it assesses and what it leaves unknown. crates/harness/examples/quote runs the whole pipeline, with a stand-in quote service.

Code coverage

Contract coverage asks which documented outcomes were seen. Code coverage asks which of the program’s own source ran, and links that to the test that ran it. It is a separate thing with a separate section on the test’s page, because it means something different.

The application collects it (Istanbul, or anything that writes LCOV) and hands it over as step attachments, in JavaScript with onAttachments. Then extensions/code-coverage reads LCOV or Istanbul’s coverage-final.json and writes results/<runner>[@platform].code.tsv (app.code.tsv for the default runner):

expectation-run expectations --docs docs --attachments captures
npx expectation-code-coverage --results docs/results/app.tsv --attachments captures \
  --revision "$(git rev-parse HEAD)" --scope "src/**, without tests" \
  --report-url "https://coverage.example.com/{run}/{slug}/"
expectation docs expectations docs

Each test’s page then has a “Code coverage” section: the source revision and scope that were instrumented, the lines, branches and functions hit at the start and after each step, what each step added, and a link to a full HTML report that is hosted somewhere else ({run} and {slug} are filled in for each test). Raw coverage files stay in the attachments directory, outside the manual.

What the section claims is limited on purpose:

  • It is observed execution. It never changes a test’s result or an expectation’s verdict, and it doesn’t say anything was asserted. A line that ran in a failed test ran.
  • Missing is not uncovered. A step with no capture, or with one that can’t be read, is shown as that. Zero lines hit and “no data” are different.
  • A step’s part is only claimed when it can be. Counters count from when the app started, so a step’s part is the difference from the capture before. If a counter goes down, the app restarted, and nothing is attributed to that step. If a step’s capture is missing, the next difference is labelled as since the earlier step it is compared with. Anything else that ran in the same window, such as background work, is in the numbers, and the page says so. With --counters per-step the app empties its counters each time it hands them over.
  • It counts for its own run and test. Like contract evidence, a capture is shown only with the run it came from and a test that hasn’t changed since.

Code coverage files are read the same way as the others: tab-separated, a few hundred characters a field, 16 MiB at most, and the report link must be an http or https address. The format is described at the top of crates/story/src/codecov.rs. Expectation doesn’t instrument the app: collecting coverage is the app’s and the driver’s job.

Writing an extension

Extensions in JavaScript can start from extensions/kit: it reads the results file, finds the attached files (refusing any path that leaves the attachments directory, links included) and writes records that can’t break the format. Expectation reads every extension’s file the same way, whatever kind it is: the file for another platform is left out, a file over 16 MiB isn’t read, fields are cut, and evidence counts only for its own run and test as it was.

An extension reads:

  • the results file (results/<runner>[@platform].tsv), for the run id, each test’s slug and fingerprint, and each step’s window;
  • the evidence: the attachments, or another tool’s capture;
  • the contract (an OpenAPI document, say).

It writes results/<name>[@platform].coverage.tsv, which expectation docs and Acceptance::publish read next to the results. Coverage files are filtered by platform the same way results are. The format is tab-separated, with - for nothing:

expectation-coverage 1
contract      <name>  <kind>  <revision>
evidence      <id>  <run>  <test slug>  <fingerprint>  <step>  <attribution>  <source>  <label>
item          <id>  <group>  <label>  <location>  <observed|not-observed|unknown>  <reason>
seen          <item id>  <evidence id>
complete      <run>  <yes|partial|no>  <note>
undocumented  <group>  <label>  <evidence id>
unmatched     <label>  <evidence id>  <reason>
excluded      <group>  <reason>
  • contract: what it is and which version: Quote API, API contract, sha256:….
  • evidence: one observation, such as a request and its response. <step> is the step it belongs to (0 for the test’s start). <attribution> says how it was tied to that step: declared (the driver captured it for that step), timed (it began and ended inside the step’s window), spans (it began in that step and ended in a later one), setup (while the test was being set up) or unassigned. <source> is live, replay, stand-in, fault (an injected failure) or unknown. <label> is what a reader sees, such as POST /quote → 429. Keep it free of secrets: a path template, not a path with ids in it.
  • item: one outcome the contract describes: a status code, an enum value, a oneOf branch. <group> gathers them (POST /quote), and <location> says where the contract defines it (#/paths/~1quote/post/responses/429).
  • seen: which evidence saw which item. Items and evidence come before the seen lines that name them.
  • complete: whether the extension had all of a run’s traffic, with every body it needed.
  • undocumented: something seen that the contract doesn’t describe, such as a status it doesn’t list.
  • unmatched: evidence the extension couldn’t place in the contract, such as a request that matches no operation or matches two.
  • excluded: a group left out of the counts on purpose, with why.

Lines of a kind Expectation doesn’t know are skipped, so later versions can add kinds. Lines it can’t read are left out and listed on the page. Every field is cut to a few hundred characters with control characters removed, ids to 128. A file over 16 MiB isn’t read.

The rules

Expectation holds every coverage file to the same rules, whatever the extension claims:

  • Evidence counts only for its own run. Its run id must be the run of the result shown for that test, and its fingerprint must be the test’s. Evidence from another run, from a test that has changed since, from a test that didn’t run, or from a step the test doesn’t have covers nothing. The page counts it under “Evidence that doesn’t count”.
  • Only evidence tied to a step counts. Evidence that names no test or step is unassigned, whatever its attribution says.
  • “Not observed” needs a complete capture of every run. It stands only if every run that ran tests is marked complete yes. Otherwise, or if some results have no run id, the item is unknown, with the reason.
  • Observed is observed, even in a failed test. The response happened. The test’s result is shown as it is, and evidence never makes a failed or unsupported test pass.
  • Counts are of what’s listed. Totals cover the items in the file, minus excluded groups. There is no percentage of a whole API.

An extension should mark an item unknown, with the reason, whenever it can’t tell:

  • a body that is missing, redacted, truncated or not JSON;
  • a schema construct it doesn’t support;
  • a stream (SSE, WebSocket) when it only reads HTTP.

A recorded response is not proof that the app showed the right thing, and evidence from an injected fault shows how the app handles an outcome, not that the real service produces it. The page marks fault evidence as injected.

In the manual

Each contract gets a page, contracts/<name>.md and site/contract-<name>.html, linked from the test report. It shows:

  • the counts, and how complete each run’s capture was;
  • one table per group: each outcome, its state, the test steps that saw it (with source and attribution), and why it is unknown;
  • what was seen but isn’t in the contract, and what matched nothing;
  • the evidence that doesn’t count and why, the excluded groups, and any lines of the file that were left out.

contracts/<name>.json has the same facts for machines. Each test page lists, under the step, the evidence that counts for it. Steps have anchors (#step-3), so links go straight there.

Everything comes from the saved files, so expectation docs rebuilds the same pages without running the app.

In CI

A suite gives CI three things to do, from cheapest to most thorough:

  1. Check the suite. No product needed, a second or two. Run it on every pull request.
  2. Run the tests. Needs the product and its driver.
  3. Keep the manual. The run writes it; CI stores or publishes it.

Check the suite

expectation check expectations

It exits 1 when the suite has errors (a conflict, a story that relies on unspecified behaviour, a word outside the vocabulary) and 0 otherwise. Warnings don’t fail it.

Run the tests

How the run is started depends on the driver:

  • A Rust test (Bindings): cargo test runs it, and assert_passes fails the test when a check fails. For a gate, use assert_passes_with(&mut driver, &opts, Policy::Required).
  • A remote driver (JavaScript, Swift, anything else): start expectation-run and the driver, as in Getting started without Rust. For a gate, pass --strict.

A run without a policy passes when nothing failed, even if nothing ran. That is the right default while a suite is being bound a word at a time, and the wrong one for a branch you release from. A run as a gate has the three policies, and Spec first says which fits when.

A GitHub Actions workflow

For a JavaScript project whose run.mjs starts the runner and the driver:

name: Acceptance
on:
  pull_request:
  push:
    branches: [main]

env:
  # The commit of Expectation the suite was written against.
  EXPECTATION_REV: <commit>

jobs:
  acceptance:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: actions/setup-node@v4
        with:
          node-version: 22

      # Built from source, so cache it: the key changes only when the pinned commit does.
      - uses: actions/cache@v4
        id: expectation
        with:
          path: ~/.cargo/bin/expectation*
          key: expectation-${{ runner.os }}-${{ env.EXPECTATION_REV }}
      - if: steps.expectation.outputs.cache-hit != 'true'
        run: |
          cargo install --git https://github.com/ptescher/expectation --rev "$EXPECTATION_REV" expectation_cli
          cargo install --git https://github.com/ptescher/expectation --rev "$EXPECTATION_REV" expectation_remote

      - run: expectation check expectations
      - run: npm ci
      - run: node run.mjs          # passes --strict to expectation-run

      # The manual and the saved results, also when the run failed.
      - if: always()
        uses: actions/upload-artifact@v4
        with:
          name: manual
          path: docs

A Rust project needs no install step: cargo test builds the harness from the project’s own Cargo.lock, and cargo run -p <your tools package> -- check expectations runs the command at the same version (see In your own project).

Keep the manual

docs/ after a run holds the manual and docs/results/*.tsv, the results it was written from. Two ways to keep them:

  • Commit them. The Markdown manual renders on GitHub, and a pull request’s diff shows how the documentation changed. expectation docs expectations docs rebuilds the manual from the saved results without running anything.
  • Publish the site. Upload docs/site/ to any static host. For readers, not authors, build the reader edition.

Screenshots can make a repository large; Screenshots in large projects keeps them in a store or a bucket.

Before either: a manual holds screenshots and, if the driver hands them over, requests and logs. Anything committed or published is visible to everyone who can see it. Read Evidence privacy first, and run CI against test accounts and fixtures.

Several runs, one manual

A unit-level run and a browser run can each cover part of one suite. Give each a name (--runner api, --runner web) and the same --docs directory, and the manual shows both. A policy judges only the run that was just made: a pass saved by an earlier run doesn’t stand in for a test that didn’t run now. See Several runners.

The expectation command

expectation checks a suite, shows its graph and plans, and writes its docs, without running anything. Running needs the system under test, so that happens through expectation_harness in your own tests or program, which saves the results for the docs.

cargo install --git https://github.com/ptescher/expectation expectation_cli

Or, from a checkout: cargo run -p expectation_cli -- <command>.

expectation --help prints the commands and expectation --version the version.

Pinning a version

A suite, the command, the runner and the client in your app should all come from one commit of Expectation. cargo install --git without a revision takes whatever main is that day, so pin it. This prints the commit main is at now:

git ls-remote https://github.com/ptescher/expectation HEAD

Install that commit, and write it down where the project keeps its setup (a script, the README, the CI workflow):

cargo install --git https://github.com/ptescher/expectation --rev <commit> expectation_cli
cargo install --git https://github.com/ptescher/expectation --rev <commit> expectation_remote

A Rust project pins the crates the same way (rev = "<commit>" beside git = …), and its Cargo.lock keeps them there. Tagged releases are listed in the changelog; once there is one, --tag v<version> does the same job as --rev.

init

expectation init              # writes expectations/turnstile.expect
expectation init <dir>

Writes a starter suite: a coin-operated turnstile with three expectations and a story, commented line by line, that checks with no errors or warnings. Edit it into your own. It never writes over a suite: a directory that already has .expect files, at any depth, is an error (exit 2).

check

expectation check <dir>

Loads the suite, checks the vocabulary, conflicts, overrides and stories, and prints every diagnostic with where it is and what to do. A suite with platforms is checked as each platform reads it. Ends with a one-line summary:

Kettle: 11 expectations in 3 features, 3 stories (3 tests); 2 exceptions; flow DAG 12 edges, 3 levels deep

Exits 1 if there are errors, so it can run in CI.

graph

expectation graph <dir>          # Mermaid
expectation graph <dir> --dot    # Graphviz DOT

Prints the flow DAG: each feature as a group, each expectation as a node (invariants as hexagons), arrows from the start and between expectations, dotted arrows for overrides, and red ones for conflicts nobody has settled.

states

expectation states <dir>                               # Mermaid state diagram
expectation states <dir> --dot                         # Graphviz DOT
expectation states <dir> --by "the screen,the dialog"  # tell states apart by these

Prints the state map: every state the app can get into from each section’s setup, and every action that moves it from one to another ([*] marks the starts). Where graph is about expectations, this is about the app: its screens and modes and how to get around them. A section whose setup another expectation Hands over to: is not a start: it is reached from there.

States are told apart by the vocabulary’s enumerated states unless --by names others, so a number like a dial’s reading doesn’t make a state per value. Name the state that is your app’s screen to get one node per screen; actions that change only what --by leaves out show as staying put.

The docs have the same map as site/states.html: drag to pan, scroll to zoom, and pick a state to see its screenshot (from a test step that was in it), what can be done there, the expectations behind each move, and the ways in. It works without JavaScript too.

plan

expectation plan <dir>
expectation plan <dir> --coverage
expectation plan <dir> --coverage --state-pictures

Prints the acceptance test each story compiles to: what’s arranged, each step, which expectations fire and what’s checked. --coverage adds the generated tests for expectations no story reaches. --state-pictures adds the ones that visit a state only so the state map has a picture of it (see Stories).

docs

expectation docs <dir> <out-dir>

Writes the manual (Markdown and the HTML site) to <out-dir>, using the results that runs have saved in <out-dir>/results/. Without results, every test shows as “not run”. Coverage files that extensions wrote there (*.coverage.tsv) each get a contract coverage page (see Evidence and contract coverage). A file that can’t be read is a warning, not an error.

  • --approved-only writes just what the suite marks Approval: approved (see Approved-only manuals); --results <dir> reads the saved results from there instead of <out-dir>/results.
  • --reader writes the edition for people who read the manual, not test it: no “How this is tested” blocks and no screenshot placeholders (see The reader edition).
  • --stylesheet <css> restyles the HTML site with your CSS file (see Your own theme). A missing, empty or malformed file stops the command before anything is written.
  • --state-shot-ratio <w:h> sets the shape of the screenshots on the state map’s cards, as width over height: 9:19.5 for a phone, 16:9, or a number like 0.46. Between 1:5 and 5:1.
  • --section <name|slug|dir>, which you can give more than once, writes a preview of just those sections and what is under them. --base-url <url> is the full manual’s address, for the preview’s links to pages it doesn’t have; without it they read as plain text. See Previews of some sections.
  • --screenshots <dir|url> says where the screenshots are, for a run that kept them in a store (see Screenshots in large projects). Give a directory and the ones the pages show are copied in. Give a URL prefix and the pages link there.
  • --expect-app-revision <rev>, --expect-data-mode <mode> and --expect-fixture <name> say what the manual is for. Each test’s page then says whether its result was run against the same, something else, or didn’t say (see What a run was against). No verdict changes.

screenshots prune

expectation screenshots prune <store> <results-dir>... [--dry-run]

Removes the screenshots in a content-addressed store, and their thumbnails, that no results file in the given directories names. Only files named by a hash are touched. With no results files it removes nothing and exits 2.

screenshots push, pull and lfs

expectation screenshots push <store> <bucket> [--dry-run]
expectation screenshots pull <bucket> <store> [--dry-run]
expectation screenshots lfs <store>

  • push and pull copy a store to or from a bucket, adding what the other side lacks and deleting nothing. They run the provider’s tool:

    • aws s3 sync for s3://…;
    • gcloud storage rsync (or gsutil rsync) for gs://…;
    • rclone copy for an rclone remote (name:path).

    A missing tool is an error that says where to get it.

  • lfs writes <store>/.gitattributes so the store’s PNG, JPEG and WebP files are kept in Git LFS. It keeps any lines already there, and running it again changes nothing.

See Screenshots in large projects.
