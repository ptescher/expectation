Expectation

The expectation command

expectation checks a suite, shows its graph and plans, and writes its docs, without running anything. Running needs the system under test, so that happens through expectation_harness in your own tests or program, which saves the results for the docs.

cargo install --git https://github.com/ptescher/expectation expectation_cli

Or, from a checkout: cargo run -p expectation_cli -- <command>.

expectation --help prints the commands and expectation --version the version.

Pinning a version

A suite, the command, the runner and the client in your app should all come from one commit of Expectation. cargo install --git without a revision takes whatever main is that day, so pin it. This prints the commit main is at now:

git ls-remote https://github.com/ptescher/expectation HEAD

Install that commit, and write it down where the project keeps its setup (a script, the README, the CI workflow):

cargo install --git https://github.com/ptescher/expectation --rev <commit> expectation_cli
cargo install --git https://github.com/ptescher/expectation --rev <commit> expectation_remote

A Rust project pins the crates the same way (rev = "<commit>" beside git = …), and its Cargo.lock keeps them there. Tagged releases are listed in the changelog; once there is one, --tag v<version> does the same job as --rev.

init

expectation init              # writes expectations/turnstile.expect
expectation init <dir>

Writes a starter suite: a coin-operated turnstile with three expectations and a story, commented line by line, that checks with no errors or warnings. Edit it into your own. It never writes over a suite: a directory that already has .expect files, at any depth, is an error (exit 2).

check

expectation check <dir>

Loads the suite, checks the vocabulary, conflicts, overrides and stories, and prints every diagnostic with where it is and what to do. A suite with platforms is checked as each platform reads it. Ends with a one-line summary:

Kettle: 11 expectations in 3 features, 3 stories (3 tests); 2 exceptions; flow DAG 12 edges, 3 levels deep

Exits 1 if there are errors, so it can run in CI.

graph

expectation graph <dir>          # Mermaid
expectation graph <dir> --dot    # Graphviz DOT

Prints the flow DAG: each feature as a group, each expectation as a node (invariants as hexagons), arrows from the start and between expectations, dotted arrows for overrides, and red ones for conflicts nobody has settled.

states

expectation states <dir>                               # Mermaid state diagram
expectation states <dir> --dot                         # Graphviz DOT
expectation states <dir> --by "the screen,the dialog"  # tell states apart by these

Prints the state map: every state the app can get into from each section’s setup, and every action that moves it from one to another ([*] marks the starts). Where graph is about expectations, this is about the app: its screens and modes and how to get around them. A section whose setup another expectation Hands over to: is not a start: it is reached from there.

States are told apart by the vocabulary’s enumerated states unless --by names others, so a number like a dial’s reading doesn’t make a state per value. Name the state that is your app’s screen to get one node per screen; actions that change only what --by leaves out show as staying put.

The docs have the same map as site/states.html: drag to pan, scroll to zoom, and pick a state to see its screenshot (from a test step that was in it), what can be done there, the expectations behind each move, and the ways in. It works without JavaScript too.

plan

expectation plan <dir>
expectation plan <dir> --coverage
expectation plan <dir> --coverage --state-pictures

Prints the acceptance test each story compiles to: what’s arranged, each step, which expectations fire and what’s checked. --coverage adds the generated tests for expectations no story reaches. --state-pictures adds the ones that visit a state only so the state map has a picture of it (see Stories).

docs

expectation docs <dir> <out-dir>

Writes the manual (Markdown and the HTML site) to <out-dir>, using the results that runs have saved in <out-dir>/results/. Without results, every test shows as “not run”. Coverage files that extensions wrote there (*.coverage.tsv) each get a contract coverage page (see Evidence and contract coverage). A file that can’t be read is a warning, not an error.

  • --approved-only writes just what the suite marks Approval: approved (see Approved-only manuals); --results <dir> reads the saved results from there instead of <out-dir>/results.
  • --reader writes the edition for people who read the manual, not test it: no “How this is tested” blocks and no screenshot placeholders (see The reader edition).
  • --stylesheet <css> restyles the HTML site with your CSS file (see Your own theme). A missing, empty or malformed file stops the command before anything is written.
  • --state-shot-ratio <w:h> sets the shape of the screenshots on the state map’s cards, as width over height: 9:19.5 for a phone, 16:9, or a number like 0.46. Between 1:5 and 5:1.
  • --section <name|slug|dir>, which you can give more than once, writes a preview of just those sections and what is under them. --base-url <url> is the full manual’s address, for the preview’s links to pages it doesn’t have; without it they read as plain text. See Previews of some sections.
  • --screenshots <dir|url> says where the screenshots are, for a run that kept them in a store (see Screenshots in large projects). Give a directory and the ones the pages show are copied in. Give a URL prefix and the pages link there.
  • --expect-app-revision <rev>, --expect-data-mode <mode> and --expect-fixture <name> say what the manual is for. Each test’s page then says whether its result was run against the same, something else, or didn’t say (see What a run was against). No verdict changes.

screenshots prune

expectation screenshots prune <store> <results-dir>... [--dry-run]

Removes the screenshots in a content-addressed store, and their thumbnails, that no results file in the given directories names. Only files named by a hash are touched. With no results files it removes nothing and exits 2.

screenshots push, pull and lfs

expectation screenshots push <store> <bucket> [--dry-run]
expectation screenshots pull <bucket> <store> [--dry-run]
expectation screenshots lfs <store>

  • push and pull copy a store to or from a bucket, adding what the other side lacks and deleting nothing. They run the provider’s tool:

    • aws s3 sync for s3://…;
    • gcloud storage rsync (or gsutil rsync) for gs://…;
    • rclone copy for an rclone remote (name:path).

    A missing tool is an error that says where to get it.

  • lfs writes <store>/.gitattributes so the store’s PNG, JPEG and WebP files are kept in Git LFS. It keeps any lines already there, and running it again changes nothing.

See Screenshots in large projects.

In your own project

The CLI is also a library: expectation_cli::main() runs the command with the process’s arguments. A workspace can ship the command as its own package, so cargo run -p <yours> -- check expectations builds it at the version the workspace locks:

// tools/expectation/src/main.rs
fn main() {
    expectation_cli::main();
}

Exit codes

CodeMeans
0Done, with no errors (there may be warnings). Also --help and --version.
1The suite has errors.
2A usage error (the usage is printed to stderr), or a directory that can’t be read.
