Executable specs

A spec a tool can check, run and publish.

You write expectations (given, when, then) in a vocabulary of declared states and events. Expectation checks them for conflicts, compiles user stories into acceptance tests, runs them against the real system through a driver, and writes the manual from the same suite.

Get started See a generated manual 

$ cargo install --git https://github.com/ptescher/expectation expectation_cli

What it is for

Spec-driven development

The spec is a checked artifact, not a document that drifts. Write behaviour before it is built (Status: pending), mark what is agreed (Approval:), and find contradictions while writing the spec instead of while debugging.

Keeping agents on task

A step that names no declared state or event is an error, and a story can't rely on behaviour the spec doesn't give. Done is a set of commands with exit codes and per-test verdicts, and "not supported yet" is reported apart from "failed". For agents.

Deterministic results

Tests are derived from the model by an algorithm, not written or sampled at run time: the same suite gives the same plans. A test continues from the last one only after observing the system is where it needs to be, and results are saved so the manual can be rebuilt.

1 Specify
Expectation: Turning the dial up starts the kettle
  Given the kettle is off
  When the dial is above 55 %
  Then the kettle is heating

Expectation: The child lock holds the kettle
  Given the kettle is off
  And the child lock is on
  When the dial is above 55 %
  Then the kettle is off

Every step is a declared state or event, so the suite is a model, not a script.

2 Check
error[conflict]: «The child lock holds the kettle»
and «Turning the dial up starts the kettle»
disagree about the kettle
 = note: both apply when the kettle is off and
   the child lock is on, and the dial is above 55 %
 = help: «The child lock holds the kettle» is the
   more specific; if it's an exception, add
   Overrides: Turning the dial up starts the kettle

Contradictions, unreachable behaviour and untested rules are caught before anything runs.

How it works

Conflicts

Conditions are sets of states, so overlaps and contradictions are exact. Exceptions are explicit with Overrides:, and they must form a DAG.

Stories

A story describes a journey. The expectations it passes through supply the checks, so it never restates the rules, and one that contradicts them is rejected before it runs.

Coverage

A flow DAG from the starting state gives every expectation a shortest route. A generated test follows it when no story does. Controls the tests never touched are listed.

Drivers

A dozen closures bind the vocabulary to a library, a game loop, an HTTP API, a browser or a device. Remote clients exist for Swift, JavaScript and Rust.

Evidence

Each step keeps what it saw: a screenshot, or for an API the request as a curl command and its response, with credentials redacted. Missing capabilities are "not supported yet".

Manual

Markdown and HTML in the user's words, with Say: and Shows: lines for what to press and what appears. Approved-only manuals are supported.

One suite, several front ends

Embed a driver in the app (Swift, JavaScript or Rust) and the same runner drives it. The demo is one kettle built three times, held to one suite.

Bind it, run it

Bind each term of the vocabulary to your system, then run the suite from a test. It fails with every broken expectation, by name.

Drivers in the guide →

let mut driver = Bindings::new(Kettle::default())
    .observe("the kettle", |k| k.phase_name())
    .set("the dial", |k, v| k.dial = v.as_f64().unwrap())
    .on("the user presses lock", Kettle::press_lock)
    .on_settle(|k| k.run_for(1.0))
    .on_screenshot(|k| Screenshot::svg(k.svg()));

Acceptance::load("expectations")?
    .with_coverage()
    .assert_passes(&mut driver, &RunOptions::default());
